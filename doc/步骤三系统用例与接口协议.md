# 步骤三：备货与物流系统用例及接口协议

范围依据：当前流程总览步骤三包含N05备货与出口单证、N06订舱/提货与运输计划、N10运输/签收/货损处理。步骤四的海关申报不在本轮实现范围，N10依赖同批真实放行；银行、税务、电子签及海关未接入时不能造成功事实。这里只交付设计、离线示例及独立测试驱动，不是生产handler或官方通道验收。

## 一、系统目标与前后置

| 用例 | 主要参与者与入口 | 前置、成功保证及失败恢复 |
|---|---|---|
| 建立批次并分配批准货物 | 供应商在交易详情中新建出运批次 | 使用已批准交易资料，累计分批数量、金额不能超限；新建的只是运输计划，尚未获准发运 |
| 修改或取消未执行运输计划 | 供应商修改；出口代理有权人员取消 | 只可修改未送审、未对外执行的计划；取消限计划或订舱阶段且尚未提货，已订舱须正式撤销凭据。结果不明时不释放数量 |
| 提交并核实备货与出口单证 | 供应商提交，独立审核员核对 | 明确销售合同、商业发票、装箱单的版本和对应批次；核实备货后批次仍在计划阶段 |
| 登记并核实订舱与提货 | 物流公司提交，独立审核员核对 | 先核实物流主体、委托关系、有效合同和备货凭据；订舱、提货分别核实，缺依据时不推进 |
| 核实运输、到达与签收事实 | 物流公司按区段提交，独立审核员核对 | 按顺序核实真实凭据；出境须同批正式放行，签收须有权收货人的凭据，通知到达不代表收货 |
| 报告并处置货损、拒收或延误 | 物流公司报告，出口代理有权人员处理 | 保留异常前进度；多个异常全部解决后才恢复。正式灭失依据齐全才记履约失败，不自动退款或付款 |
| 查询批次进度与恢复原受理 | 供应商、物流公司查本方记录，审核员用内部入口 | 超时后保留原请求编号、内容和版本标记查原回执；当前进度不能单独证明某次提交已成功 |

供应商和物流公司在本阶段各自提交负责的凭据，步骤一仍只有供应商和付款方首次填报。供应商提前沟通并收集收货人资料，物流公司取得签收材料后交内部核实，不强制收货人另开账户。三单引用原文件的具体版本；没有OCR时仍须人工核对扫描件内容。

## 二、实体、版本与状态

使用权威领域模型物流四表：`logistics_shipment_tab`、`logistics_shipment_item_tab`、`logistics_transport_leg_tab`、`logistics_event_tab`。本轮不增加核心列或业务表。物流码表在`assets/domain-model.js`明确，和Proto枚举一致：

| 状态码 | 含义 | 正常进入条件 |
|---|---|---|
| 1 | 计划中 | 原子创建批次、分配、运输区段 |
| 2 | 已订舱 | 同版备货与有效委托链齐、真实订舱核实 |
| 3 | 已提货待发运 | 订舱后真实提货核实；纠正旧“已提货却叫待提货”的歧义 |
| 4 | 运输中 | 首段真实启运；出境须正式放行 |
| 5 | 已到达 | 所有必需区段完成、末段真实到达 |
| 6 | 已签收 | 收货主体及数量差异处理、授权签收证据核实，成功终态 |
| 7 | 异常处理中 | 有效异常事件，冻结原阶段 |
| 8 | 已取消 | 未执行且无未知任务，必要撤销证据齐，取消终态 |
| 9 | 履约失败 | 实质灭失等责任/保险/审批闭环，失败终态 |

备货核实仅事件3，订舱4、提货5、启运6、到达7、签收8、异常9、处置10、取消11、失败12；计划创建1、更正2。`event_status_code=1`表示已核实，待审声明不进核心事实事件。`allocation_status=1`有效、2撤销，与资金域分配码不混用。重复、伪造或验签失败拒绝/隔离，不将货物改成“履约失败”。

计划资源字段逐一映射：`tradeRevisionNumber`定位原因2快照内容修订，`approvedSnapshotNumber`和完整已批准商品/主体放入不可变中间件计划封套；批次根保存交易/内容修订、角色1发货人、角色3收货人、角色5物流及序号、起终点/计划日期。`allocations`映射商品分配表（序号/数量/单位/金额/CNY）；`legs`映射区段表（顺序/方式/起终点/计划UTC时刻）；外部实际时刻只能经核实事件写，不是PUT字段。

物流表没有version列：同库受理账本的单调序号＋冻结完整计划生成`planRevision`；强ETag由批次最后受理序号/事件尾派生，避免ABA。纯查询不产生新序号。计划PUT前封存完整旧计划到不可变中间件封套，之后才替换当前分配/区段投影；执行后不可覆盖。修改导致旧待审证据失效的情况本版直接拒绝修改；先形成独立退回决定，再新提交。分配取消更新2保留原行；成功执行不释放已履约数量。

`transport_leg_number`没有独立对应主键列，明确为`shipment_number#leg_sequence_number`可逆引用；批次号服务端生成且≤32 ASCII字符，区段1..65535，合计≤38字符。禁止客户端传入不属于本批次的区段号。承运号在核实订舱事件的受控证据封套中解析后写`carrier_booking_number`，不能信任任意“我已订舱”字符串。区段方式码1海/2空/3陆/4铁。

金额必填`DECIMAL(20,2)`，数量`DECIMAL(20,6)`，协议为十进制字符串且禁止指数/负数/超精度。所有批次有效数量与金额不超同原因2快照对应批准行，单位完全一致；不擅自汇率折算或重新定价。分配不校验单价乘数量强等，避免批准金额存在已明确舍入时重复计价；批准总量/总额上限是硬约束。日期为中国业务自然日，实际时刻UTC，计划/实际前后次序均检查。

批准后更正不能靠新修订号“重置可发货数量”：若同交易已有其他批准内容修订的有效分配，暂以`PLAN_FROZEN`阻断新建或换绑，保留已执行历史，待明确商品版本对照和累计迁移规则后另行设计，不擅自释放旧货物/恢复额度。本轮不实现跨批准版本迁移；不可把“同快照上限”当作整交易跨版本不超发的充分条件。

### 必要中间件而非新领域实体

复用步骤一二受理/确认/文件任务机制，新增业务类型分支，不新起微服务：

- 受理账本唯一`(subject,audience,key)`，保存方法/规范化路径/原标签/业务HMAC、最小响应、准确Location、单调序号；根为交易，批次关联明确。
- 不可变计划封套唯一`(shipment,planRevision)`，含批准快照号、完整原计划、必要主体/商品只读快照、上一计划引用；不得把当前JSON当历史唯一来源。
- 证据提交唯一submissionId，以及`(可信来源主体,shipment,kind,sourceReference)`稳定去重键；原源键同文回原资源，异文拒绝。提交保存计划版/原文件引用/声明人/发生时刻；审核决定另行追加，退回不覆盖。
- 决定唯一`submissionId`最终决定；退回后另建新提交与源引用，旧结论不可改。备货只供应商；订舱/运输/异常仅核实的本物流主体或内部有权代录，代录保留原来源、核查人及说明，独立审核不得自己审自己。
- GET提交资源包含不可变`reviewResult`（决定、退回理由、审核时刻、审核身份引用及核查依据），未审时不存在；补正通过`replacesSubmissionId`关联同批同种已退回提交，必须重新确认新内容。不得通过修改原源键内容或重用旧确认绕过退回。
- 异常封套绑定原事件、冻结恢复阶段与未闭环集合。新异常发生在7时继承最初冻结阶段；不能由客户端自报恢复目标。
- 文件共用持久任务和确切版本，不将HTTP客户端重试当唯一恢复。无生产worker/自动调度时明确未实现。

## 三、门禁与交易原子性

所有写先验证当前身份/受众/对象权限，再BEGIN查原受理；同文原回执优先旧标签/过期确认，但不绕过当前授权。新请求固定锁序：交易根→本单批次号排序→分配→区段→文件→确认→任务/受理。创建尚无批次时交易根串行化同单累计；后续查询同根有效分配总额在锁内执行，不仅锁单批次。原请求再查以防并发首查为空。取批次号使用同库计数行，业务/计数/回执同COMMIT，计数锁不调用外部I/O。

业务事务明确使用READ COMMITTED；加交易根锁后再读受理与批次游标，商品分配逐行`SELECT ... FOR UPDATE`当前读后定点求和。不能在默认REPEATABLE READ下先普通SELECT建立旧快照，再误以为“等到交易根锁”后的普通SUM已看见前一个批次提交；真实并发验证已捕获并修正这一超分配风险。若以后改隔离级别，必须保留这些当前读与根锁不变量。

订舱输入显式`bookingReference`（≤64），核实后写区段订舱号；追踪号`trackingReference`（≤128，不含令牌）、地点`locationCode`与`legSequence`结构化录入，不能依赖从任意文件/OCR或statement提取。消息`sourceReference`只作去重/追溯，不当作身份凭据。核实前这些字段留在待审提交封套，不能提前写成实际承运事实。

确认凭据复用步骤一外部与步骤二内部operation-confirmations入口，强认证＋具体内容确认；绑定方法/路径/幂等键/原If-Match/类型化正文摘要。创建标签针对交易根，其他写针对批次根；读资源返回该标签。独立审核人身份由可信认证上下文取得，不接收actorId等可伪造字段。供应商不需自持签名设备，实名授权、强认证、明确意图及不可改审计构成操作证据；HTTPS非抗抵赖证明。机构可选RSA/ECC或SM2/SM3，签名算法/法定效力另行接入。

首次新建前尚无批次号，复用步骤二`GetTradeContractBasis`（`GET /api/v1/trades/{trade_number}/contract-basis`）读取原因2批准快照、商品/主体及交易根ETag，页面直接关联这份已有Proto，不另造准备订单/物流占位实体。后续GET批次读取批次ETag；创建本身不修改交易正文，累计分配仍在交易根锁下重新核查。

S3/扫描及外部核实均事务外；用准备时固定版本回到事务重查。事务内只核实本地已冻结、权限有效、用途正确、摘要一致的文件引用及**独立核实结论**，不能以“存在PDF/扫描通过”证明内容真实。缺真实合同生效/适用、官方放行、签收授权，分别`LOGISTICS_GATE_MISSING`、`CLEARANCE_REQUIRED`、`EVIDENCE_NOT_VERIFIED`，不得接受客户端布尔值代替。

多区段：后段提货须前段到达；各段实际时刻按本地已核实事件顺序，旧通知不能回退。首段启运置4，末段到达且各段完整置5，最终有权收货人确认才6；中间段到达只写段事实不改批次5。出境区段由服务端受控地点/线路识别，不能用客户端mode/statement绕开海关门禁。异常7期间新推进被阻断，处置后继续按独立事件顺序，不通过“处置”直接签收。

COMMIT响应丢失查主库原键；DB锁等待上限1秒、事务设计预算2秒。GET客户端5秒/应用4秒；业务写10秒/8秒；共用文件确认15秒/12秒。扫描连接3秒、读10秒；存储单次连接3秒/读30秒的本机验证设置不等于生产HTTP同步预算，文件确认必须异步任务返回202/任务状态或沿现步骤一已定义任务资源恢复，不持业务锁等待。后台固定键/租约/fencing/有界8次及退避复用步骤一设计；本轮简单验证不再声称验证所有进程恢复分支。

## 四、REST、RPC与错误

协议：[logistics.proto](../proto/trade/logistics/v1/logistics.proto)。九个方法均显式`ReqMsg`/`RspMsg`，`google.api.http response_body: "resource"`，HTTP纯资源JSON不加RPC外壳。单体外部/内部两受众，不是模块RPC。

新建POST201＋准确Location，原幂等重放200＋原Location；PUT200；GET200。未知资源404；缺认证401、对象越权403；缺If-Match428、旧标签412；异文409；领域状态/超量409；缺业务证据422；存储/DB暂不可用503；超时504（结果可未知，不能假定回滚）。未声明查询参数拒绝400。不接受任意PATCH状态或PUT实际时刻。

决定/处置/取消资源使用本次`acceptanceId`作为Location末段稳定标识，冻结回执不跟随当前批次进度重算；本版不额外暴露这些命令资源的单项GET，结果未知以原命令重入恢复，当前正式进度和原证据审查结果分别通过批次/上下文/证据GET读取。接口不支持的GET返回405而不是暗示已实现查询。

| 稳定码 | HTTP / gRPC | 恢复 |
|---|---|---|
| IDEMPOTENCY_CONFLICT / SOURCE_CONFLICT | 409 / ALREADY_EXISTS | 恢复原文或新业务意图，不覆盖原结果 |
| PRECONDITION_REQUIRED / REVISION_CONFLICT | 428或412 / FAILED_PRECONDITION | GET合并后重新确认，原未知命令先原键恢复 |
| ALLOCATION_EXCEEDED / PLAN_FROZEN / SHIPMENT_STATE_CONFLICT | 409 / FAILED_PRECONDITION | 补正或等待原任务核实；不重复取号、不释放未知占量 |
| LOGISTICS_GATE_MISSING / CLEARANCE_REQUIRED / EVIDENCE_NOT_VERIFIED | 422 / FAILED_PRECONDITION | 补齐真实同批、同版、用途及独立核实证据 |
| INVALID_ARGUMENT | 422 / INVALID_ARGUMENT | 修正字段路径/精度/日期，不静默舍入 |
| LOCK_TIMEOUT / DEPENDENCY_UNAVAILABLE | 503 / UNAVAILABLE | 原键有界恢复，不无限重试 |
| OUTCOME_UNKNOWN | 无响应或504 / DEADLINE_EXCEEDED | 主库原键恢复，禁止认为取消或另发 |

HTTP问题详情与RPC`RpcFailure`沿用步骤一字段结构（type/title/status/reason/fieldViolations/retryable/traceId），不在日志复制材料正文/令牌。请求头`Authorization`、`Idempotency-Key`、`If-Match`、`X-Confirmation-Id`（GET无后三项），RPC对应小写metadata；确认入口本身不递归要求确认。无有效确认不得运行示例命令。

完整逐接口RESPONSE/cURL、请求/响应和RPC metadata/deadline见[HTTP全集](examples/step3/http-reference.md)、[HTTP JSON](examples/step3/http-examples.json)、[RPC JSON](examples/step3/rpc-examples.json)。只含原创合成材料和不可用身份占位，不是有效签名、真实外部回执或已执行成功证明。读取/创建/改版/审核例展示不同时间点的独立输入，不能串联成真实已履约交易。

## 五、验证与限制

独立验证器`infra/local/verify-step-three.py`将当前权威DDL中的物流四表和必要交易/文件表复制到新的随机库，不在`export_trade`建表/改数据。检查真实S3版本/ClamAV、精确DECIMAL、跨批并发、原键回放、回滚/标签/缺证据阻断，结果由`--output`显式指定保存路径，不自动写入交付目录。

合成原因2批准快照仅是测试前置，不代表真实业务批准。合成用户/确认/核查人只证明测试逻辑，不证明生产认证、法定签约或主体授权。真实外部合同、银行、海关、税务均未接入，不制造它们的成功证明。保留隔离数据库；本轮随机S3确切版本清理后，测试库引用不可作为可用业务样本。无后台生产API、真实电子签、生产权限或自动调度验收。
