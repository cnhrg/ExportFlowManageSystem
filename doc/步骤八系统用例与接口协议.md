# 步骤八：四流核对、差异案件及正常结案

## 1. 边界及事实所有权

本步骤先核对交易相关资料和资金账务，再处理差异，条件齐备后申请正常结案。用例分别说明如何查看全部资料、生成逐项报告、登记差异并分派处理人、暂停指定业务、补交凭据、申请更正并重审、解除某项暂停、关闭已解决案件、申请结案、独立审批，以及查询历史和原请求结果。业务说明和黑盒图使用这些操作名称；数据库字段、状态码和锁序见后续实现约束。

对应N22/N23；这是单体离线设计、协议与隔离验证驱动，不是已部署REST/RPC、IAM、外部监管或银行通道。图默认原图70%，每目标独立黑盒SSD与实际消息级展开；模型全局`EXPORT_STEP_EIGHT_USECASES_MODEL`及CommonJS，产物全局`EXPORT_STEP_EIGHT_ARTIFACTS`。生成器和逐项测试见`doc/sql/step8/`。

不提供特殊结案执行入口，不设isClosed/isHold；正常结案8→10终态不可重开，暂停与生命周期正交。无垫资、授信、透支或换汇。税务终局拒绝/不适用不自动算正常完成，更不绕道“特殊结案”。完整业务用例与具体时序以模型生成的`doc/examples/step8/s8-*-system.mmd`、`*-implementation.mmd`为准。

交易域`trade_event_tab.event_payload`保存类型化不可变报告（18）、正常结案申请（19）、退回决定（20）；正式结案仍17。报告与申请不能藏技术受理ledger。合规`compliance_discrepancy_case_tab`及`compliance_disposition_event_tab`拥有案件、分派、补正、暂停、解除、关案决定及证据；业务事实在`decision_snapshot_json`及`affected_contexts_json`，不是泛化任务JSON。资金差异归资金域，合规不得伪造到账、解除资金锁或冲正凭证。

## 2. 源一致性及核对报告

每个源为稳定`type/id/revision/hash/sourceEventTail`；还冻结各类完整排序对象ID集合及其摘要和规则版。覆盖批准交易快照/商品行、有效合同及正式委托、全部批次及物流事件、全部申报及修订/A确认/正式办理/放行、附件2/附件3交付接收、来款/分配/三桶/付款与A到账、服务费、凭证/分录/冲正/账户、证明/退税案件/提交/官方事件/退款归属、全部异常与合规案件及有效原因。

空集合不等于未接入；未接入、权限无法核实、范围规则未确认、源事件尾不明均为`unknown`并阻断。外部“成功”须可核实的真实来源和确切证据版本；内部合成文件、通知接收、超时、技术投递成功均不构成外部成功。

报告逐项为`pass/fail/unknown`，保存观察值、期望值、差异、证据、来源和规则。没有客户端可设置`allPassed`或`isClosed`。最终短事务重读源向量及**集合**，防新增对象绕过版本比较。各域受控写必须锁同一交易根后修改业务事实；不遵循此协调契约的外部异步读不能证明结案一致性，应失败关闭。

资金逐项使用CNY定点字符串并以数据库DECIMAL/应用十进制精确计算：

1. 银行毛额=逐笔真实分配+未匹配；未匹配不擅自作为本交易可用款。
2. 本交易真实已分配净额=受限+可用+付款锁额+已核实支付/退回；事件流水重算等于余额投影，负桶拒绝。
3. 结算应付=已核实实际支付+尚未支付/明确差异；银行扣款不是A到账。正常结案不允许未决付款、未释放锁额或未核实到账。
4. 实际银行费用与D服务费分账结算分别勾稽；服务费须关联D授权及来源可用余额，不得伪造银行扣款或减少A合同应付。
5. 每张凭证借贷平衡；账户从已过账分录重算；冲正保留原分录并关联反向凭证；只有总借贷相等不足以证明正确。
6. 退税金额/批准/实际到账与账户归属分别核实；供应商收款不增加出口代理D货款账户。

## 3. 多原因暂停、解除、关案和更正

每个暂停由原案件中的不可变`holdReference`唯一标识，精确列出所属域/业务对象/版本/作用操作范围。多个案件和同案多个原因并存；新执行必须查询全部有效原因，不只查案件状态。暂停决定、传播接收、所属域执行是不同事实。原因解除申请不改变门禁；独立复核通过只解除该原因，逐目标执行确认前仍阻断。其他原因不受影响。

关案和解冻互不替代；合规关案可保留有效暂停，其解除另走原申请独立复核。资金差异必须资金域实质关闭及独立复核，不能由合规备注“已解决”代替。未知外部执行不因关案或技术任务失败变成明确失败。

更正申请须原节点/原批准版/完整影响对象及依赖边；独立批准只批准更正范围。原节点建立新修订重审，旧报告和受影响未执行批准失效。已执行不可逆事实不撤写；结果未知先原号查单；下游失效/重审传播未确认时禁止执行。重新核实后产生新源事件和新报告，旧快照永久可查。

## 4. 正常结案申请与独立决定

申请人选定报告18及摘要、规则版、源向量和全部对象集合。锁根后重新核验最新事实、资金守恒、账务平衡、真实外部证明、无未解异常/暂停/传播/未知执行，全部满足才追加19，交易仍8。独立审批人与申请人不同；批准时再次核验，不能沿用申请时的判断。新增对象、状态/事件变化、规则版过期均阻断；退回写20及逐项理由，不结案。通过写17与8→10同本地事务。新意图不能再改终态，但首次原键原文受理始终可恢复。

## 5. MySQL/文件恢复及并发

单体、同一MySQL、READ COMMITTED。事务外完成读取/报告计算/S3确切VersionId摘要校验/ClamAV扫描。业务短事务顺序：

1. 当前身份/受众/对象授权；BEGIN后先查主体+受众+原键，命中同文回放首次冻结结果，异文409。先重入后新版本、已消费确认及终态检查。
2. 共享固定顺序：交易根（多单按二进制业务号升序）→物流/关务/税务根→资金范围/事务/分配→account id升序→案件、事件尾、文件元数据、确认及受理；根锁后再次当前读原键。不同幂等键也受根锁协调。全部回执写和源版本变化同样必须同交易根协调，不能因是后台回执而跳过根锁；最终结案重验全部对象集合。
3. 当前读`FOR UPDATE`源版本与完整对象集合、有效原因/传播、独立人员及确认精确绑定；新写检查If-Match，失配412，未提供428。
4. 业务不可变事件、必要投影、确认消费和最小冻结回执原子COMMIT。死锁/唯一键冲突整笔回滚后新事务只恢复原键，不在半事务继续。
5. COMMIT结果未知返回503/原请求恢复路径，不能另键再做。读取当前状态不能证明某命令已成功。

文件在事务外，复用既有上传/确认持久任务、租约、扫描状态、确切VersionId及摘要；未就绪返回可恢复错误。后台按原任务退避恢复，浏览器退出不丢任务；达到预算报警，不伪造文件成功。测试只清本run确切S3版本，保留随机隔离库，不访问或修改export_trade。

## 6. REST/RPC、响应和错误

协议`proto/trade/reconciliation/v1/reconciliation.proto`全部内部受众，显式ReqMsg/RspMsg，`response_body:"resource"`；HTTP正文是领域资源，RPC包装`resource`。查询只读200；POST创建不可变申请/报告/决定201及可GET的Location。通用处置统一可GET的`.../dispositions/{disposition_number}`；禁止以`POST /execute`等命令入口替代资源。原受理路径仅当前主体/受众可见，不能猜别人的键。

元数据：`authorization`、写入的`idempotency-key`、`if-match`、`confirmation-id`；确认绑定当前主体/受众/方法/路径/正文摘要/原键/标签和时效。真实身份验真、独立复核授权由既有IAM/确认机制提供，示例无可用凭据。客户端/应用读取5000/4000ms、写10000/8000ms，RPC显式deadline；应用预算包含连接、锁等待、事务、序列化。原键重试总预算内至多三次，100/300ms抖动；文件任务单独持久预算，不在业务事务重试外部I/O。

继承步骤一错误：400参数/未知字段、401身份/确认、403权限、404不可见、409同键异文/状态门禁、412陈旧标签、422业务证据、428缺标签、429限流、503依赖/提交未知、504超时。RPC对应INVALID_ARGUMENT/UNAUTHENTICATED/PERMISSION_DENIED/NOT_FOUND/ALREADY_EXISTS/FAILED_PRECONDITION/RESOURCE_EXHAUSTED/UNAVAILABLE/DEADLINE_EXCEEDED；细分业务码及重试见`error-examples.json`。不得将EXTERNAL_EVIDENCE_MISSING伪装为可重试成功或自动补造证明。

逐接口完整RESPONSE、cURL、RPC request/response/metadata/deadline见`doc/examples/step8/http-reference.md`与`http-examples.json`、`rpc-examples.json`。所有样例为独立不可执行合成结构例，并非完整正常结案E2E成功轨迹。当前unknown报告的正常结案申请明确422拒绝，HTTP统一`application/problem+json`及`trade.filing.v1.HttpProblem`；RPC仅`error={code:"FAILED_PRECONDITION",details:trade.filing.v1.RpcFailure}`，不存在response/resource。另存`failure-examples.json`，不伪造申请已成功。

## 7. 验证与未实现

`node doc/sql/step8/generate.cjs --check`检查持久化产物一致；`node doc/sql/step8/verify.cjs`检查资源/协议/双图、完整集合/陈旧报告、多原因和独立复核规则，结果输出到终端。`infra/local/verify-step-eight.py --output /tmp/export-trade-step-eight-result.json`仅在当前最终DDL摘要确认后运行真实随机隔离MySQL/S3/ClamAV验证，结果只写入显式指定路径。

验证驱动不实现完整生产接口/身份/官方接入/工作调度。测试分别标注数据库硬约束、应用门禁、隔离合成事件；外域尚未接入，仅证明缺证据、unknown、资金不平、并发陈旧和终态原回放阻断，绝不宣称已完整通过正常结案端到端。

## 8. 封闭JSON映射与公共规范集成

权威公共规范为`doc/领域拆分评估与交易域设计.md §11`。HTTP/RPC camelCase按字段逐一映射数据库snake_case，不将HTTP开放对象直接塞JSON。`trade_event18.event_payload`严格顶层为`payload_schema_version,report_schema_version,rule_version,source_version_vector,object_sets,checks,evidence_references`。源向量每项严格`context_code,business_number,revision_reference,content_hash,event_tail_reference`；对象集合每项严格`type,object_ids,hash`；checks各项为Proto `CheckItem`的snake_case字段，`result`用1通过/2不通过/3未知。报告内容hash由持久化封套确定，不另造互相矛盾摘要列。

`EvidenceReference.documentPurposeCode`按公共材料用途1..25核验，映射`FileRef.document_purpose_code`；`sha256`映射公共`content_digest`。示例原创文件用途19仅为**合成供应商差异书面说明**，不是真实签署确认或银行/官方证明，报告仍unknown。不得省略公共FileRef用途或仅因有扫描通过文件就认定本用途真实有效。

合规事件除公共必填`action_code,result_code,reason_code,actor_reference,decided_at`及已有可选字段，还需公共规范统一扩展**必填**`decision_type`及`decision_details`封闭分支（不增加DDL列）。本步类型白名单如下，所有分支拒绝未知字段：

| decision_type | decision_details字段及业务动作码 |
|---|---|
| assignment | `assigned_to,due_at,reason`；action1 |
| hold_decision | `reason,affected_contexts`，后者是完整`AffectedContext`含操作白名单及确切源引用；根列affected_contexts仅作公共接收索引；holdReference为本事件业务号；action2、result2或3 |
| gate_acknowledgement | `decision_reference,hold_reference,phase`（received/applied），多目标另绑定`target_context_code,target_business_reference,source_revision_reference,source_event_reference`；action4、result1，不表示实质处置通过 |
| remedy | `original_disposition_reference,substantive_dispositions,evidence_references,explanation`；action3提交/result1；独立实质核实另记action4 |
| remedy_decision | `application_reference,outcome,reason,source_version_vector,object_sets,evidence_references`；action4/result2或3；对应独立remedy-decisions资源，不自动解除暂停 |
| correction_application | `original_node,affected_contexts,dependency_edges,source_version_vector,object_sets,rule_version,reason,evidence_references`；action5/result1 |
| correction_decision | `application_reference,outcome,source_version_vector,object_sets,rule_version,invalidated_references,reentry_node,propagation_targets,reason,evidence_references`；action6/result2或3；通过也不批准更正后的事实 |
| release_application | `hold_reference,source_version_vector,object_sets,rule_version,substantive_dispositions,evidence_references`；action7/result1 |
| release_decision | `hold_reference,application_reference,validation_basis,source_version_vector,object_sets,evidence_references`；action8/result2或3；validation_basis须具体依据，非可执行“已核实”布尔值 |
| case_closure_application | `source_version_vector,object_sets,substantive_dispositions,money_difference_closure,evidence_references`；action9/result1表示申请，不能关案 |
| case_closure_decision | `application_reference,scope,source_version_vector,object_sets,evidence_references`；action9/result2或3，与解除独立 |

公共`affected_contexts_json`仍严格`context_code,business_reference,scope_code,action_code,expected_acknowledgement?`；具体操作、源修订及依赖边放对应decision_details中已声明的`AffectedContext/SourceReference`结构，不滥加开放根属性。`SourceReference`及`SourceVector`严格等同Proto的snake_case字段；来源真实性由所属域而非本JSON自证。

隔离验证仅用单交易/单目标、内部文字差异的缩减分支，暂不声称多目标传播、完整更正图执行、真实资金实质解除已实现。必须先由主线程把上述业务封闭分支合入公共§11再作为集成契约使用；不得退化为技术ledger临时存放。

完整机器可读分支必填/可选字段、动作及结果码、值类型：`doc/examples/step8/compliance-decision-contract.json`；所有分支拒绝未知属性。`gate_acknowledgement`目标定位字段对多目标生产动作条件必填，单目标缩减验证可从原决定唯一解析。`money_difference_closure:null`只允许原案件确无关联资金差异，不得借null绕过已知资金差额。
