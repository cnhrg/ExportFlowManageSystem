## 0. 适用场景与前提

**本手册的全部结论都建立在下表的前提上。前提变了，结论要重新评估。**

| 维度 | 取值 | 推论 |
|---|---|---|
| 业务量 | **300 单/天** | 峰值 QPS ≈ **0.025**；放大 1000 倍也才 25 QPS → **吞吐永远不是瓶颈** |
| 热点 | **不存在热点账户** | 无需分片、无需账户串行化队列 |
| 首要目标 | **账务准确性第一** | 准确性 > 可用性 > 成本 > 性能 |
| 可用性 SLO | **4 个 9（99.99%）** | 年度不可用预算 **52.56 分钟**，每日 **8.64 秒** |
| 并发控制 | **全量显式加锁（悲观锁）** | 放弃乐观锁重试，统一走 `FOR UPDATE` |
| 部署形态 | **单库单写**（三年内不引入分片） | 读写分离保留，但目的不是读扩展 |
| 服务区域 | 中国 UTC+8 + 中亚 UTC+4:30~+6 | 业务日必须**按区域时区**切账 |
| 字符集 | utf8mb4 | 俄/泰/繁全在 BMP 内，2~3 字节，零风险 |
| 数据量 | 10 年后约 **438 万行 / 2 GB** | 单表轻松承载 |

**核心判断：在这个量级上，架构的复杂度预算应该几乎全部花在正确性和可恢复性上。性能优化是伪需求。**

## 1. 十条铁律

**任何设计、优化、评审意见与这十条冲突时，以这十条为准。**

| # | 铁律 | 违反后果 |
|---|---|---|
| 1 | **钱不能算错** —— 金额一律 `DECIMAL`，全局唯一舍入点，尾差"最后一份兜底" | 对不平账，且**无法从数据反推原因** |
| 2 | **账不能改** —— 流水 append-only，错误走反向分录冲正 | 失去对账基准，审计不可追溯 |
| 3 | **事不能重** —— 幂等靠**数据库唯一索引**，不是"先查后插" | 并发下重复入账 |
| 4 | **事不能丢** —— `flush_log_at_trx_commit=1` + `sync_binlog=1` + 备份演练 | 已确认事务丢失 |
| 5 | **锁要串行** —— 账户写操作统一走 `FOR UPDATE`（唯一索引等值）+ 全局按 `account_id` 升序 | 丢失更新 / 死锁链 |
| 6 | **时间要唯一** —— 事件时刻存 UTC（`DATETIME(3)`），业务归属日按区域（`DATE`） | 账务日期错误（比乱码严重得多） |
| 7 | **主键要稳定** —— 代理主键自增，业务唯一性靠独立 `uk_*`；`id` 绝不出现在对外 API | 主键要改 = 重建半个系统 |
| 8 | **字符要精确** —— 业务主键列用 `utf8mb4_0900_bin`（NO PAD） | 大小写折叠撞唯一键，且错误信息看不出原因 |
| 9 | **变更要可逆** —— 所有 DDL 走 `gh-ost` 零停机，变更单含回滚脚本 | 一次 5 分钟故障 = 烧掉 10.5 天可用性预算 |
| 10 | **错误要可查** —— 失败必须留痕（审计 / 事件 / 指标），不留痕的失败等于没发生 | 慢性渗漏耗尽错误预算 |

## 2. 架构决策与不可逆约束

### 2.1 决策一：不做分库分表、不做分区、不做归档

| 方案 | 结论 | 理由 |
|---|---|---|
| 分库分表 | ❌ **不引入** | 峰值 QPS 0.025，分片收益为 0；却要付出跨片事务、脑裂、三年后无法回退的全部代价 |
| 范围分区 | ❌ **不引入** | 10 年后仅 438 万行 / 2 GB |
| 冷热分离归档 | ❌ **暂不引入** | 2 GB 数据随便查 |
| 只读副本 | ✅ **保留，但目的不同** | 不是读扩展，而是**报表隔离 + 在线备份 + 故障切换候选 + 演练** |

**数据量测算**（每单 4 条分录、每行 500B）：

| 时间 | 交易笔数 | 分录行数 | 数据量 |
|---|---|---|---|
| 3 年 | 328,500 | 1,314,000 | 0.61 GB |
| 5 年 | 547,500 | 2,190,000 | 1.02 GB |
| 10 年 | 1,095,000 | 4,380,000 | **2.04 GB** |

**重估触发条件**（满足任一即重新评估，写进 ADR，季度巡检）：

- [ ] 单表行数 > 5,000 万 或 单表数据量 > 50 GB
- [ ] 核心表 DDL 变更耗时 > 30 分钟
- [ ] 备份窗口无法在业务低峰内完成
- [ ] 峰值写入 QPS > 200（当前值的 8000 倍）

### 2.2 决策二：全量显式加锁（悲观锁）

**为什么在这个量级下悲观锁优于乐观锁**：

| 维度 | 乐观锁（CAS） | 悲观锁（`FOR UPDATE`） |
|---|---|---|
| 300 单/天下重试率 | 极低 | **无重试** |
| 正确性 | 依赖"读到的版本是最新的" | **数据库层面串行，天然无丢失更新** |
| 失败模式 | 重试耗尽后放弃，语义复杂 | 锁等待超时，语义简单可枚举 |
| 心智负担 | 每个写路径都要写重试循环 | 一次加锁，之后随便改 |
| **最大隐患** | **"漏写重试" = 静默丢更新** | "锁范围过大" = 持有时间长 |

**乐观锁最大的隐患是漏写重试**：某个开发在 `update ... where version = ?` 影响 0 行时直接抛异常或静默跳过，在低频下可能几个月才暴露一次。悲观锁把这个隐患整个移除了。

**`version` 字段的用途因此改变**：不再是并发控制手段（全量悲观锁不需要），保留在可变表上用于**检测"绕过应用层直接改库"**（运维脚本、DBA 直连）。保留成本几乎为零，收益是发现暗改的能力。

### 2.3 决策三：自增主键（`AUTO_INCREMENT`）

**在"单库单写 + 不分片"前提下，自增 ID 是最优解。**

| 维度 | 自增 ID | 雪花 ID / 号段 |
|---|---|---|
| **余额序列自洽校验** | ✅ `ORDER BY id` **严格单调**，零假阳性 | ⚠️ 同毫秒靠低位递增，跨节点/时钟回拨可能乱序 → **偶发"假断裂"** |
| 分片前提下的全局冲突 | ❌ 不存在（不分片） | ✅ 无此问题 |
| 写入 | ✅ 顺序插入，无页分裂 | ⚠️ 趋势递增但非严格连续 |
| 运维可读性 | ✅ ID 区间 ↔ 时间区间一一对应 | ⚠️ 需额外解码 |
| 游标分页 | ✅ `WHERE id > ?` **绝不漏同毫秒记录** | ⚠️ 可能漏 |
| 跨环境数据搬运 | ⚠️ ID 冲突（以业务唯一键为准） | ✅ ID 天然全局唯一 |

**第 1 行是决定性的**：余额序列自洽校验是"三道防线"的第 3 道，在"准确性第一"的前提下，让它从"近似"变成"精确"是值得的。

**切换触发条件**（满足任一立即启动评估）：

| 触发 | 切换 |
|---|---|
| 引入分库分表 | ⛔ 立即 |
| 引入第二个写节点（写扩展 / 多活多写） | ⛔ 立即 |
| 从单库扩为多库**且需跨库 ID 全局唯一** | ⛔ 立即 |
| **只读副本（读写分离）** | ✅ **不触发**（只有主库写） |
| 单库扩容 / 加索引改字段 | ✅ 不触发 |

**平滑切换靠三条纪律撑着**（已在执行的规范）：**禁物理外键 + 不硬编码 ID + id 不对外暴露**。破一条，切换成本就从"改一个 DAO 基类"变成"重建半个系统"。

**切换路径**（不可直接改主键类型）：
```
Step 1  新增 ext_id BIGINT UNSIGNED, 应用层发号器赋值
Step 2  回填历史数据 ext_id (分批 + 断点续跑)
Step 3  双写 (id 与 ext_id)
Step 4  读切换 (跨表引用改用 ext_id)
Step 5  观察 1~2 个发布周期
Step 6  id 降级为普通列
```

### 2.4 决策四：全库 UTC 存储 + 按区域切账

**三维分工，不可互相推导**：

| 维度 | 语义 | 类型 | 时区 | 字段 |
|---|---|---|---|---|
| **事件时刻** | 事情客观发生的瞬间，全球唯一 | `DATETIME(3)` | **统一 UTC** | `created_at` / `updated_at` / `occurred_at` |
| **业务归属日** | 这笔算哪一天的账（**是约定不是事实**） | `DATE` | **按区域本地时区** | `transaction_date` / `accounting_date` |
| **会计期间** | 哪个账期（月） | `CHAR(6)` yyyyMM | 随业务归属日 | `accounting_period` |

**规则**：

1. 时间戳统一 UTC 存储，展示层转换
2. 业务日期按**客户/账户所属区域**的本地日历计算
3. 一个客户的所有交易用同一区域的会计日
4. 切账时点按区域本地时间（`system_region_tab.cutoff_time`，常见 04:00，不是 00:00）
5. 本地时间 < 当日切账时点 → 归属上一日
6. **跨区域转账：两侧各自按自己区域记，记账日可能差 1 天**

**为什么 `TIMESTAMP` 不用**：

> ⚠️ 常见论证"2038 截断"在本系统 **不成立**（系统不活过 2038），已作废。
> 保留的唯一理由是：**TIMESTAMP 的读值取决于 `@@session.time_zone`** —— 同一行数据在不同连接里读出来不一样，且**不报错、不告警、不留痕**。
>
> 若强制 session tz 恒为 UTC，TIMESTAMP 与 `DATETIME(3)` 行为完全一致。此时选 `DATETIME(3)` 的理由是**故障安全**：配置被改坏时，它什么都不发生，而 TIMESTAMP 会静默偏移。
>
> **不是"TIMESTAMP 是错的"，是"两个都对，我选失败模式更安全的那个"。**

**跨区记账日归属规则**（一次定死）：

| 维度 | 归属 | 理由 |
|---|---|---|
| 付款方/发起方侧 | 发起方 `region_code` | 记账主体原则 |
| 收款方侧 | 收款方 `region_code` | 独立法人主体，独立记账 |
| 会计期间 | 各自独立 | 可能落在不同月 |
| 跨境手续费 | 单独计费，不摊入双方 | 避免两边金额不等导致对账不平 |

**副作用（必须提前知道）**：监管报送会出现两笔不同日期的交易 —— 这是正确的，不是重复；客户查"我的交易"看到日期不一致，前端要说明"按本地记账日显示"；报表必须按区域出，不能简单合并。

### 2.5 决策五：utf8mb4 + 列级 collation

**字符集层面零风险**：俄文（U+0400–U+04FF）、泰文（U+0E00–U+0E7F）、繁体中文（U+4E00–U+9FFF）**全部在 BMP 内，最多 3 字节**。utf8mb4 的 4 字节只出现在补充平面（emoji、`𠮷`、生僻新造字）——那恰恰是用户自由输入字段最可能出现的。

**风险全部在排序规则（collation）及其副作用**：

| 风险 | 说明 | 对策 |
|---|---|---|
| **业务主键撞唯一键** | `utf8mb4_0900_ai_ci` 下 `'ИВАН0001' = 'иван0001'` 为真 | 业务主键列用 **`utf8mb4_0900_bin`** |
| **PAD SPACE 陷阱** | `utf8mb4_bin` 是 PAD SPACE，`'ACC1' = 'ACC1 '` | 用 **`utf8mb4_0900_bin`**（NO PAD，8.0.17+） |
| **泰文排序无解** | MySQL 无泰文 collation，东南亚只有越南语 | **应用层 ICU 排**，DB 存预计算排序键 |
| **组合字符被切碎** | 泰文/阿文按码位截断会切出半个字形 | 组合文字列**禁止前缀索引** |

**MySQL 8.0 collation 库存要点**：
- ✅ 俄文有专用规则：`utf8mb4_ru_0900_ai_ci` / `utf8mb4_ru_0900_as_cs`（UCA 9.0 + 俄语定制）
- ❌ 泰文**没有**（全部按码位序，前置元音 เ แ โ ใ ไ 开头��词被排到辅音前）
- ❌ `utf8mb4_general_ci` 在 8.0 已弃用
- ❌ `utf8mb4_unicode_ci` 仅 5.7 兼容场景使用

**collation 分配规则**：

| 字段类别 | collation | 说明 |
|---|---|---|
| 账号、客户号、交易号、凭证号、分录号、**幂等键**、渠道流水号、批次号、码表编码 | **`utf8mb4_0900_bin`** | 精确匹配，大小写敏感 |
| 密码、Token、API Key、签名 | **`utf8mb4_0900_bin`** | **严禁任何 `_ci`** |
| 证件号/手机号/银行卡的 hash 列 | **`utf8mb4_0900_bin`** | hash 本身区分大小写 |
| 姓名、地址、描述、备注（展示类） | `utf8mb4_0900_ai_ci` | 搜索友好 |
| 俄文名称排序 | `utf8mb4_ru_0900_ai_ci` | 若主客户群是俄语区 |

**一个库只能有一个"展示文本" collation**，否则 JOIN 报 `ERROR 1267 Illegal mix of collations` 且索引失效。

### 2.6 决策六：单库单写 + 4 个 9 的拓扑

**明确推荐：优先选云厂商托管的高可用 MySQL（跨 AZ 同步复制版），而不是自建 MGR。**

| 维度 | 托管（RDS/PolarDB 等） | 自建 MGR + Orchestrator |
|---|---|---|
| 自动故障转移 | ✅ 厂商负责，有 SLA 兜底 | 需自己保证切换器、VIP、仲裁不出问题 |
| 备份 / PITR | ✅ 自动化 + 可视化 | 自己写脚本，自己验证 |
| 脑裂防护 | ✅ 厂商处理 | 自己处理（自建最容易死的地方） |
| 值班要求 | 厂商 7×24 | **需要自己 7×24 响应** |
| 成本 | 较高（闲置付费） | 单机便宜，但要算人力 |

**核心判断**：300 单/天 几乎不需要 DBA 团队，但 4 个 9 需要 7×24 故障响应 —— 这两件事矛盾。托管服务用"钱"换掉"人和值守"。

> **合规前提**：金融行业常有数据本地化要求。**若合规不允许用公有云托管，必须自建** —— `MGR 3 节点 + 半同步复制 + Orchestrator/Patroni + ProxySQL + 独立备份机`，并且**必须每季度演练一次主库宕机切换并记录 RTO**。不演练的高可用等于没有高可用。

**底线要求**：
- 跨可用区部署，**不能是同一物理机上的两个进程**
- 复制必须**同步或半同步**（RPO = 0 或 ≤ 1 秒）
- 自动故障转移，人工不介入
- 备份独立于主从链路

## 3. 命名规范

### 3.1 结构

```
<业务域全称>_<实体全称>[_<限定词>]_<类型标记>
     customer   master                tab
```

**两条要求的张力与解法**：

> "所有表名后缀 `_tab`" 与 "表名避免缩写" 存在内在冲突 —— `_tab` 本身就是 `table` 的缩写。
>
> **解法：把 `_tab` 定义为「类型标记」而非「缩写」**，与 `.vue` / `.java` / `.tsx` 同类 —— 属于**受控词表**，不参与缩写检查。
>
> - ① **实体名部分必须全称，零缩写** ← "避免缩写"的真正落点
> - ② **类型标记是受控词表**，豁免缩写检查
> - ③ 靠后缀区分对象类型，**避免视图与表重名**（MySQL 8.0 视图与表共用命名空间）

### 3.2 业务域词表（7 个，封闭）

| 域 | 含义 | 覆盖 |
|---|---|---|
| `customer` | 客户信息 | 客户主档、联系人、证件、协议 |
| `account` | 账务 | 账户、账务分录、记账凭证、余额 |
| `payment` | 支付交易 | 交易、渠道流水、对账差异、费率 |
| `batch` | 跑批与日终 | 跑批任务、会计日历、计提、快照 |
| `message` | 消息 | 发件箱、收件箱、订阅、模板 |
| `admin` | 管理后台与审计 | 审计日志、可用性事件、变更登记 |
| `system` | 系统基础配置 | 码表、区域、参数、字典 |

**规则**：域词表**封闭**，新增域必须评审；一个域内表数 ≤ 5；**域归属按"数据的业务归属"划分，不按"谁在用"划分**（例：区域定义放 `system` 而非 `batch`，因为它本质是系统配置，跑批只是消费者）。

### 3.3 类型标记词表

| 标记 | 含义 | 生命周期 | 业务代码可直写 |
|---|---|---|---|
| `_tab` | 实体表 | 长期 | ✅ |
| `_view` | 视图（只读） | 长期 | ❌ |
| `_tmp` | 临时/中转表 | 可重建 | ❌ |

- **所有实体表必须以 `_tab` 结尾，无例外**
- 视图必须以 `_view` 结尾；禁止"视图不带后缀"
- 临时表必须以 `_tmp` 结尾，且**必须在 runbook 中写明重建方式**
- 存储过程/函数/事件：`sp_<动作>_<对象>` / `fn_<动作>_<对象>` / `ev_<时机>_<对象>`

### 3.4 字段命名

| 规则 | 示例 |
|---|---|
| 全小写下划线，见名知意，禁拼音缩写 | ✅ `customer_id` ❌ `kh_id` |
| 布尔用 `is_` / `has_` / `enable_` 前缀 | `is_reconciled` / `is_closed` |
| 金额以 `_amount` 结尾 | `transaction_amount` / `difference_amount` |
| 数量以 `_count` 结尾 | `affected_transaction` / `success_count` |
| 时间点以 `_at` 结尾 | `created_at` / `started_at` / `sent_at` |
| 日期以 `_date` 结尾 | `transaction_date` / `business_date` |
| 期间以 `_period` 结尾 | `accounting_period`（`CHAR(6)` yyyyMM） |
| 编码以 `_code` 结尾 | `channel_code` / `dictionary_code` |
| 状态用 `_status` / `_state` | `customer_status` / `account_status` |
| 类型用 `_type` | `customer_type` / `transaction_type` |
| **序号用 `_number`，不用 `_no`** | `transaction_number` / `batch_number` / `entry_number` |

**为什么统一 `_number`**：`_no` 本身是 `number` 的缩写，与"避免缩写"冲突；字段名长度成本极低（+4 字符）而歧义成本不低。历史通用的 `id_no`（证件号）统一为 `identity_number`。

**受控技术标记**（豁免缩写检查，与 `_tab` 同理）：`_id`（标识符）、`_hash` / `_cipher`（哈希/密文列）、索引名前缀 `uk_` / `idx_`。

### 3.5 索引与约束命名

```
uk_<实体核心词>_<列语义>     唯一索引
idx_<实体核心词>_<列语义>     普通索引
chk_<实体核心词>_<语义>       CHECK 约束
```

**"实体核心词" = 去掉域前缀和类型标记后的部分**：

| 表 | 核心词 | 索引示例 |
|---|---|---|
| `account_ledger_entry_tab` | `ledger_entry` | `idx_ledger_entry_account_date` |
| `payment_transaction_tab` | `payment_transaction` | `uk_payment_transaction_no` |
| `system_dictionary_item_tab` | `dictionary_item` | `idx_dictionary_item_type_status_sort` |

**规则**：索引名**必须带实体核心词**（多个表都有 `idx_status_created` 时无法区分）；最长 42 字符（上限 64）；联合索引只写有区分度的前导列。

### 3.6 长度约束

| 对象 | 上限 | 当前最长 | 余量 |
|---|---|---|---|
| 表名 | 64 | `payment_reconcile_difference_tab` = 32 | 32 |
| 列名 | 64 | `compensated_transaction_count` = 30 | 34 |
| 索引名 | 64 | `idx_dictionary_item_type_status_sort` = 39 | 25 |

## 4. 建表规范

### 4.1 公共字段

```sql
`id`          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键, 自增ID',
`version`     INT UNSIGNED     NOT NULL DEFAULT 0      COMMENT '版本号, 不用于并发控制(用悲观锁), 仅用于检测绕过应用层的直接改库',
`deleted_id`  BIGINT UNSIGNED  NOT NULL DEFAULT 0      COMMENT '逻辑删除标记 0=存活, 删除时置为本行id',
`created_by`  VARCHAR(64)      NOT NULL DEFAULT 'system' COMMENT '创建人(工号/系统标识)',
`created_at`  DATETIME(3)      NOT NULL DEFAULT (UTC_TIMESTAMP(3)) COMMENT '创建时间 UTC',
`updated_by`  VARCHAR(64)      NOT NULL DEFAULT 'system' COMMENT '更新人',
`updated_at`  DATETIME(3)      NOT NULL DEFAULT (UTC_TIMESTAMP(3)) ON UPDATE (UTC_TIMESTAMP(3)) COMMENT '更新时间 UTC',
```

**按表类型裁剪**：
- **append-only 表**（流水/日志/快照）不加 `updated_at` / `version` —— 它们永远不会更新，加了反而误导
- **流水表不加 `updated_by`**
- 主键统一 `BIGINT UNSIGNED` + `AUTO_INCREMENT`

### 4.2 NULL 策略

**默认 NOT NULL。** NULL 在金融表里是 bug 温床：
- `COUNT(col)` 忽略 NULL，`SUM` 忽略 NULL，口径容易算错
- 索引中 NULL 参与比较，统计信息失真
- Java 层映射到包装类型，多一层 NPE 风险

**例外仅三种**：JSON 快照、开放区间的结束日期（`maturity_date`）、尚未确定的外部单号。

**"我不知道"和"我填了 0"在业务上必须区分时，才用 NULL。**

### 4.3 类型选型

| 规则 | 说明 |
|---|---|
| 金额 → `DECIMAL(20,2)` | 币种最小单位为分。数字资产/高单价用 `DECIMAL(32,18)`，但要压测乘法精度 |
| 利率 → `DECIMAL(9,6)` | 年化 6 位小数足够 |
| 汇率 → `DECIMAL(20,10)` | 汇率可能 1 位也可能 8 位小数 |
| 比例 → `DECIMAL(9,6)`，不存 `%` | 避免"存的是比例还是百分数"事故 |
| 数量 → `INT` / `BIGINT UNSIGNED` | |
| 布尔 → `TINYINT UNSIGNED` 0/1 | 不用 `BOOLEAN` |
| 状态/类型 → `TINYINT` + 码表 | **禁 `ENUM`**（加值要 DDL）；**禁 `VARCHAR` 存状态** |
| 字符串 → `VARCHAR(n)` 必须有明确上限 | 禁 `TEXT` 存业务码值 |
| 大字段 → 拆独立表 | 合同正文、影像件、报文原文一律拆表，核心表只留 `file_id` |
| 时间 → `DATETIME(3)` | **禁 `TIMESTAMP`**（读值依赖会话时区） |
| 日期 → `DATE` | 业务归属日 |
| 期间 → `CHAR(6)` yyyyMM | 会计期间 |
| 精度 → `DATETIME(3)` | **禁 `DATETIME(6)`**（微秒无业务意义，徒增 3 字节） |
| 存储时间 → 禁 `VARCHAR` | 索引失效 + 格式不一致 |

### 4.4 金额与舍入

- **全局统一 `RoundingMode.HALF_UP`**，写在 `Money` 值对象 / `BigDecimalUtil` 里，禁止各处 `setScale(2, ...)` 散落
- **舍入点必须唯一**：中间步骤舍入一次还是最后一步？必须明确。常见做法是"中间过程保留全精度，仅在落库/展示时舍入"，但分摊/计息逐期舍入会产生尾差
- **尾差处理**：多笔分摊到 N 份必然产生分位尾差。标准做法是"前 N-1 份按规则舍入，最后一份取总额 - 已分配合计"，保证合计精确相等。**这条规则必须写进代码规范并有单测覆盖**
- **币种最小单位不同**（JPY 无小数位、KWD 3 位）时，精度与舍入规则按币种配置，不能全局硬编码 2 位

### 4.5 时间与时区

**三层落地**：

| 层 | 做法 |
|---|---|
| **存储** | `DATETIME(3)` 存 UTC；`DATE` 业务归属日；`CHAR(6)` 会计期间 |
| **连接** | session tz 恒为 UTC（4 处对齐）+ JDBC `forceConnectionTimeZoneToSession=true` |
| **应用** | Java 只用 `Instant`/`OffsetDateTime`；DB 默认值用表达式 |

**建表默认值用表达式，不依赖会话时区**：
```sql
-- ❌ 依赖会话 time_zone
`created_at` DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
-- ✅ 不依赖会话 time_zone (MySQL 8.0.13+ 表达式默认值)
`created_at` DATETIME(3) NOT NULL DEFAULT (UTC_TIMESTAMP(3))
`updated_at` DATETIME(3) NOT NULL DEFAULT (UTC_TIMESTAMP(3)) ON UPDATE (UTC_TIMESTAMP(3))
```
**把正确性从"配置必须对"变成"配置错了也不会错"。**

**DB 函数层**：

| 函数 | 行为 | 规范 |
|---|---|---|
| `NOW()` / `CURRENT_TIMESTAMP` | 会话时区 | ❌ 用 `UTC_TIMESTAMP(3)` |
| `CURDATE()` / `CURRENT_DATE()` | 会话时区 | ❌ 用 `UTC_DATE()` |
| `SYSDATE()` | 求值瞬间，STATEMENT binlog 下主从不一致 | ❌ 禁用 |
| `UNIX_TIMESTAMP()` / `FROM_UNIXTIME()` | **受会话时区影响** | ⚠️ 跨时区业务判断禁用 |
| `TIMESTAMPDIFF(unit, a, b)` | 返回 **b - a** | ✅ 差值计算用这个 |

**Java 侧禁用 `LocalDateTime` 写库**：
```java
// ❌ 灾难: LocalDateTime 无时区信息, Timestamp.valueOf 按 JVM 默认时区解释
//    JVM 是 +08:00 时, 写进去的 09:00 被当作 UTC 存 → 实际偏 8 小时
LocalDateTime now = LocalDateTime.now();
// ✅ 正确
Instant now = Instant.now();
```

**连接层四处必须同时对齐，缺一即偏差**：

| 层 | 配置 |
|---|---|
| MySQL 服务端 | `default-time-zone='+00:00'`（**不依赖 OS 时区**，容器重启会重置） |
| JDBC | `connectionTimeZone=UTC&forceConnectionTimeZoneToSession=true`（Connector/J 8.0.23+） |
| JVM | `-Duser.timezone=UTC` |
| 连接池 | 初始化时 `SET time_zone='+00:00'` 兜底 |

**查询规范**：
- **时间范围统一用半开区间** `>= start AND < end`，**禁 `BETWEEN`**（漏 23:59:59.001~.999）
- **禁在 WHERE 里对时间列套函数**（`YEAR()` / `DATE_FORMAT()` / `DATE()`）→ 索引失效
- 高频按月分组用生成列 `stat_month CHAR(6) AS (DATE_FORMAT(transaction_date,'%Y%m')) STORED` + 索引
- **期末加月会截断**（`DATE_ADD('2026-01-31', INTERVAL 1 MONTH)` = `2026-02-28`）→ 计息/分期**必须从原始起算日重算**，不能从上次日期累加

### 4.6 字符集

```sql
ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci
```

**层级**：服务器 → 数据库 → 表 → 列，**就近覆盖**。建表时**表级显式声明**，不依赖继承（否则上层是 latin1 就静默出错）。

**列级 collation 按 §2.5 的分配规则显式声明**，共 48 处。

**字符集相关的坑**：

| 坑 | 表现 | 对策 |
|---|---|---|
| `utf8` 实际是 utf8mb3 | emoji / 生僻字存不进 | 一律 `utf8mb4`；utf8mb3 在 8.0.28+ 已弃用 |
| `utf8mb4_general_ci` | 8.0 已弃用；德语 ß 判错；中文排序乱 | 用 `utf8mb4_0900_ai_ci` |
| 组合字符 | 泰文 `กิ` = 2 码位；`CHAR_LENGTH` 返回码位数 | 长度按码位数×1.5 估；**禁前缀索引** |
| emoji ZWJ 序列 | `👨‍👩‍👧` = 5 码位 18 字节 | `VARCHAR` 留足；二进制排序会拆开 ZWJ 序列 |
| 双重编码 | 客户端按 latin1 解读 utf8mb4 再转一次 | 自检：`CHAR_LENGTH` 明显大于预期即中招 |
| 连接层不一致 | 乱码 | 四处对齐 + `SET NAMES utf8mb4` |

**字节估算修正**：utf8mb4 最多 4 字节只是**上限**。俄文 2、泰文/繁中 3；但泰文因组合字符实际码位约是用户字符数的 1.3~1.8 倍，**泰文列按 3 字节 × 1.5 系数估**。

### 4.7 逻辑删除与唯一索引

**常见错误解法**：唯一索引改成 `(customer_no, deleted_at)`，靠 MySQL 允许多个 NULL 实现"未删除唯一"。**这是错的** —— NULL 与 NULL 不相等，唯一性对存活行完全失效。

**正确解法（`deleted_id` 方案）**：
```sql
`deleted_id` BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '逻辑删除标记: 0=存活, 删除时置为本行id',
UNIQUE KEY `uk_customer_no` (`customer_no`, `deleted_id`)
```
- 存活行 `deleted_id=0` → `(customer_no, 0)` 唯一 → **唯一性真实生效**
- 删除时 `UPDATE ... SET deleted_id = id` → `(customer_no, id)` 唯一 → **释放号段且可回溯**

> 金融主档更推荐：**不物理删除也不逻辑删除，用状态机**（`customer_status=3 销户`），另加审计留痕。只有监管明确要求可删除的场景才用上述方案。

### 4.8 CHECK 约束

MySQL **8.0.16+** 才真正支持（8.0.16 之前解析后忽略！）。用于守住业务不变量，是廉价的最后一道防线：

```sql
CONSTRAINT `chk_account_balance` CHECK (`balance` >= 0)
CONSTRAINT `chk_amount_positive` CHECK (`amount` > 0)
```

**应用层校验会漏**（批量导入、脚本修数、DBA 直连），DB 约束不会。

### 4.9 禁止物理外键

1. 分库分表后跨库外键无法建立
2. 级联动作在金融场景往往危险（误删主表 → 级联删流水，是灾难）
3. 每行写入都要检查父表存在性，高并发下带来额外锁与 IO
4. DDL 变更被外键卡住

**替代**：应用层保证 + 每日跑批做孤儿数据校验（`LEFT JOIN` 统计 + 告警）。

## 5. 索引规范

1. **联合索引最左前缀**：`WHERE a=? AND b=? AND c BETWEEN ? AND ? ORDER BY d` → 索引 `(a,b,c,d)`，**等值在前、范围在中、排序列在后**
2. **覆盖索引**：查询需要的列都放进索引可避免回表
3. **等值列在范围列之前**（范围列之后的列无法用于等值查找）
4. **排序方向与索引顺序一致**，避免 `ORDER BY` 触发 filesort
5. **索引列禁止函数、禁止隐式类型转换**。`WHERE DATE(created_at)='2026-01-01'` 必然全表扫；`WHERE amount = '100.00'` 会让比较转 DOUBLE，索引失效
6. **前缀索引**：`VARCHAR(200)` 存报文摘要时用 `KEY idx_x (col(64))`；**组合字符文字列（泰文/阿文）禁用**
7. **索引数量**：本场景写入量极小，**放宽到 ≤ 8，允许冗余覆盖索引** —— 查询简单性比写放大更重要
8. **不要在区分度低的列上建索引**（如 `deleted_id`）；正确做法是放到联合索引末尾
9. **禁止隐式排序**：`ORDER BY` 未命中索引会产生临时表 + filesort。分页用**游标分页**（`WHERE id > ? ORDER BY id LIMIT n`），不用大 `OFFSET`
10. **禁止 `SELECT *`** 在核心表使用 —— 无法走覆盖索引，且大字段破坏行外存储效率

**数据量极小带来的红利**：可以**鼓励冗余字段免联表**（`customer_no` / `account_no` / `customer_id` 直接冗余在流水表），减少出错面。**注意：冗余是给查询用的，不是给 JOIN 用的** —— 冗余列直接 SELECT，不要为了 JOIN 再连一次。

## 6. 金融核心表设计

### 6.1 账户表 `account_tab`

- 三值分离：`balance`（账面）、`available_balance`（可用）、`frozen_amount`（冻结）。**可用 ≠ 账面 − 冻结 是常见 bug 源头**，建议 CHECK 或定期跑批校验
- 余额**不设 CHECK 非负**的场景要明确列出（如透支账户允许为负），不要一刀切
- 乐观锁 `version`：`UPDATE` 必须带 `WHERE version = ?`，影响 0 行即重试
- 币种 `CHAR(3)` ISO-4217；**建议一账户一币种**（`currency` 入唯一键），跨币种通过交易表记录，不做账户内折算
- ★ **这是全库唯一需要加锁的表**

### 6.2 账务分录 `account_ledger_entry_tab` —— 系统的灵魂

- **借贷方向用 `direction` + 正数 `amount`**。永远不要用有符号金额表示方向 —— 余额计算事故的头号来源
- **`balance_after` 余额快照**：分录落库时记录该笔之后的余额。这一列让对账、客诉追溯、余额推演从"跑全量流水"变成"查一行"。**高价值列，勿删**
- **凭证 + 分录两级**：一次业务一个 `voucher_no`，多账户多方向拆多笔分录。业务方只认凭证，财务方只认分录
- **`idempotency_key` 唯一索引**是防重复入账的最后一道闸。键的构造规则要统一：`域 + 业务类型 + 外部请求号 + 子流水标识`，**绝不能只用一个粗糙的业务单号**（否则一笔业务拆多笔分录时会互相冲突）
- **`request_hash`**：同一幂等键但报文 hash 不同，说明是"同号不同内容"的重放或上游 bug，**必须拒绝并告警**，不要静默返回原结果
- **冲正**：`reversal_of` / `reversed_by` 双向记录。已记账分录永不修改、永不删除
  - **唯一允许的 UPDATE**：冲正时回写 `entry_status` + `reversed_by`，仅此两字段、仅此一次
  - 这条豁免**必须写进数据访问层白名单**（DAO 只暴露 `markReversed(entryNo, reversalEntryNo)`，不提供通用 `update`），否则 append-only 形同虚设
  - 更严格的做法是只留 `reversal_of` 单向指针，**物理上零 UPDATE**
- **`accounting_period`** 固化记账期间，月结后禁止修改

### 6.3 凭证 `account_voucher_tab`

一次业务一笔凭证，汇总多笔分录。状态机：`1记账中 → 2已记账 → 3已冲正 / 4失败`。

### 6.4 交易表与账务表分离

`payment_transaction_tab`（渠道交互、状态机、风控、路由）与 `account_ledger_entry_tab`（账务事实）是**两张表**：

- 交易状态会变（处理中→成功→冲正），账务分录不会变。混在一张表会导致 UPDATE 泛滥，破坏 append-only
- 交易表行数增长最快、变更最频繁；账务表要求不可变。分开才能各自优化
- 两者通过 `voucher_no` 关联

### 6.5 幂等设计（三层）

| 层次 | 手段 | 作用 |
|---|---|---|
| 接口层 | 幂等键透传 + 唯一索引 | 拦截重复提交（最外层防线） |
| 事务层 | 同事务内写业务表 + `message_outbox_tab` | 保证"业务成功但消息丢失"的最终一致 |
| 消费层 | 消费方按 `message_id` 去重 | 挡 MQ 重投递 |

**不要只靠"先查后插"防重** —— 两个并发请求同时"查不到"然后都插入。**必须靠数据库唯一索引。** 查+插只能用于返回友好提示。

### 6.6 状态机

- 状态用 `TINYINT`，流转集中在一个枚举/状态机类里，**禁止在 Service 里散落 `if (status == 1) status = 2;`**
- 状态跳转要校验合法性（非法跳转抛异常并告警）
- 终态清晰（成功/失败/关单），并配套**悬挂态处理**（`transaction_status=3 未知(待查单)` 必须有主动查单/超时补偿任务，否则是黑洞）

### 6.7 跑批 `batch_task_tab`

- `uk_batch_task_code_date(task_code, business_date)` 保证同任务同业务日只跑一次（跑批幂等）
- `lock_owner` + `lock_expire_at` 实现分布式锁
- `total_count` / `success_count` / `fail_count` 记录执行统计，失败必须落 `error_message` 并可重入
- 日终顺序（计息 → 手续费 → 计提 → 对账 → 快照 → 报表）要在设计文档中固化，任务间有依赖
- 批量任务按 100~1000 条一批提交，批间记录进度（`batch_number`）

### 6.8 审计 `admin_audit_log_tab`

- append-only，字段级 `before_data` / `after_data` / `changed_fields`
- 记录操作人、角色、IP、`trace_id`、结果
- **敏感字段（身份证、银行卡、手机号）在审计快照中必须脱敏** —— 审计表往往比业务表权限更宽，是泄露高发区
- 审计表本身不允许 UPDATE/DELETE，清理走分区或归档

## 7. 显式加锁规范

### 7.1 加锁五律

```
1. 加锁只加在 account_tab, 流水表永不加锁
2. 只锁本次交易实际涉及的账户, 不多锁一行
3. 必须在事务内, 锁必须通过 AccountLockService 获取
4. 全局按 account_id 升序加锁, 排序逻辑集中在一处
5. FOR UPDATE 必须命中主键或唯一索引的等值条件
```

### 7.2 加锁强制入口（比"规范要求"有效 100 倍）

**光写规范没有用，必须在代码结构上做到"想不加锁都难"。**

```
❌ 禁止: DAO 层暴露通用 updateById / update(entity)
✅ 要求: 账户表只有两个写入口

AccountLockService:
  ├─ lockForUpdate(accountNo)      → 统一加锁 + 返回锁对象
  ├─ AccountLockService.executeLocked(accountNos, businessLogic)
  │     → 内部: 按 account_id 升序加锁 → 执行 → 提交/回滚 → 释放
  └─ account_tab 的 UPDATE 语句只允许出现在这个类里
```

**规则**：
- 账户表的 `UPDATE` 语句在代码库中**只出现一次**，用 ArchUnit / 静态扫描在 CI 卡住其他引用
- 所有跨账户写操作（转账、代付、冲正、计息）必须经 `executeLocked`
- 业务代码**不允许**直接写 `account_tab`

### 7.3 锁顺序（防死锁第一道防线）

**全局唯一加锁顺序：`account_id` 升序。**

```java
List<Long> ids = accountNos.stream()
    .map(this::resolveId)          // 先解析 id
    .sorted()                       // 关键：按主键升序
    .toList();
for (Long id : ids) {
    jdbc.queryForObject(
        "SELECT id, account_no, balance, available_balance, frozen_amount, version " +
        "FROM account_tab WHERE id = ? FOR UPDATE", lockRowMapper, id);
}
```

**必须用 `account_id` 排序，不能用"付款方 → 收款方"这种业务顺序**：
- 业务顺序随交易方向变化 → A→B 和 B→A 形成经典循环等待
- `account_id` 与业务无关，全局稳定 → 任何两个事务的加锁序列要么相同要么可比较，**死锁在理论上被消除**

> 业务代码应调用 `executeLocked(List<accountNo>, logic)`，由它内部排序。**排序逻辑绝不能散落到业务代码里。**

### 7.4 唯一索引等值定位 —— 最容易被打破、后果最严重

> **规则：所有 `SELECT ... FOR UPDATE` 必须使用主键或唯一索引的等值条件。**

```sql
✅ SELECT ... FROM account_tab WHERE id = ? FOR UPDATE
✅ SELECT ... FROM account_tab WHERE account_no = ? FOR UPDATE
❌ SELECT ... FROM account_tab WHERE customer_no = ? FOR UPDATE      -- 非唯一 → 间隙锁
❌ SELECT ... FROM account_tab WHERE id BETWEEN ? AND ? FOR UPDATE   -- 范围 → 间隙锁
❌ SELECT ... FROM account_tab WHERE account_no LIKE 'A%' FOR UPDATE  -- 前缀 → 间隙锁
```

**为什么这条最重要**：非唯一索引或范围条件下的 `FOR UPDATE` 会加**间隙锁（Gap Lock）**，锁住索引记录之间的空隙。后果：
- 锁范围从 1 行膨胀到几百行
- RR 下间隙锁与插入意向锁互斥 → 其他事务的 `INSERT` 被阻塞
- 间隙锁是当前读，**不参与死锁检测**，容易形成难以复现的锁等待堆叠
- 账户表是热点表，一旦被间隙锁覆盖，会牵连同账户的**所有**并发写入

**这条规则破一次，整个加锁方案就退化成"高并发下的间隙锁地狱"，而排查工具查不出来。**

> 配套检查：CI 静态扫描所有 `FOR UPDATE`，校验 WHERE 条件命中主键或以 `uk_` 开头的唯一索引。命中失败直接卡构建。

### 7.5 锁范围

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| `SELECT * FROM account_tab WHERE customer_id = ? FOR UPDATE` | 锁住该客户所有账户 | 只锁交易实际涉及的账户 |
| `SELECT * FROM account_ledger_entry_tab WHERE ... FOR UPDATE` | 锁住流水表，范围巨大且无意义 | 流水表只读不加锁（append-only 天然无并发写冲突） |
| 先 `SELECT` 再 `SELECT FOR UPDATE` | 两次查询间有窗口 | 一次 `FOR UPDATE` 拿到最新值 |

**判据**：只有"读-改-写临界区"才需要加锁。流水表是 append-only，插入不冲突（唯一索引除外），**永远不需要加锁**。

### 7.6 超时与重试

```sql
innodb_lock_wait_timeout = 5    -- 默认 50 太长
```

**为什么不能留 50 秒**：锁等待期间事务持有连接和（可能）其他锁。堆积效应：

| `innodb_lock_wait_timeout` | 1 小时内最多堆积的等待事务 |
|---|---|
| 1s | 3600 |
| 3s | 1200 |
| **5s** | **720（推荐）** |
| 50s（默认） | 72 |

**一次 50 秒的锁等待超时 = 烧掉 5.8 天的年度可用性预算。** 必须短，快速失败 + 快速重试。

```java
// 重试策略
- 捕获 SQLState: 40001 / 1213 (死锁) / 1205 (锁等待超时)
- 最多重试 3 次, 指数退避 + 随机抖动: base 20ms, factor 2, jitter ±50%
- 总重试时长上限 2 秒
- 重试期间必须重新走 executeLocked (重新加锁), 不能复用已持有的锁对象
- 3 次仍失败 → 返回"系统繁忙, 请稍后重试", 记 ERROR 日志 + 上报监控
```

### 7.7 死锁处理

- 死锁在全局锁顺序下应当**极少发生**。一旦频繁出现，说明有人违反锁顺序规范 —— **修代码，不是加参数**
- 应用必须能识别 1213 并重试
- **监控项**：`Innodb_deadlocks` 计数器，**目标值 0**。任何非零都要能定位到具体 SQL

### 7.8 批量场景

**绝不能**"循环里每笔一个事务"或"一个大事务锁几千行"。

```java
for (List<Payee> batch : partition(payees, 200)) {     // 每批 200 笔
    accountLockService.executeLocked(
        batch.stream().map(Payee::accountNo).toList(),
        () -> { for (Payee p : batch) { doPay(p); } }
    );
}
```

- 单事务批量上限：**200 笔**
- 批量总笔数无上限，但必须**分批提交 + 进度可断点续跑**
- 批量失败**必须记录明细**，不能只记一个错误码

### 7.9 读写分离与 read-your-writes

| 场景 | 读哪个 |
|---|---|
| 刚扣款完返回给用户的余额 | **必须读主库** |
| 写后立刻的校验查询 | **主库** |
| 交易明细列表、历史对账查询 | 从库 |
| 报表、日终统计 | 从库 |
| 风控/反洗钱实时规则 | **主库** |

**规则：写操作后的第一次读必须走主库。** DAO 层提供 `findForUpdate`（主库）与 `find`（可路由从库）两个明确方法，不让调用方自己判断。

**主从延迟必须监控并告警**（阈值 1s），超限时路由自动降级为全部读主库。

### 7.10 隔离级别

**核心账务库用 `REPEATABLE-READ`**：

- 全量悲观锁下，RC 与 RR 的 `SELECT ... FOR UPDATE` 加锁行为**完全一致**（都是 current read）
- RC 的唯一优势是"少间隙锁"，但**在唯一索引等值查询下 RC 和 RR 都不加间隙锁** —— 优势在本场景不存在
- RR 提供**事务内一致快照**：事务内多次普通 SELECT 看到同一快照，不会出现"读余额"和"读分录汇总"来自不同时点的撕裂
- RR 的强隔离更符合"准确性第一"的产品定位

**唯一附加约束**：所有 `FOR UPDATE` 必须走唯一索引等值定位。

**热点账户串行化**：本场景无热点账户，不需要。但若将来出现超大客户，走**单账户串行化队列**（按 account_id 分段锁），而不是靠数据库重试硬扛。

## 8. 事务与并发

### 8.1 事务边界

- **一次业务 = 一个本地事务**，写库 + 发消息用 outbox 模式
- **禁止在事务里调用外部接口**（渠道、第三方）—— 外部调用不可回滚，必然造成长事务与不一致。正确顺序：事务外调用渠道 → 事务内落库 → outbox 异步通知
- 事务要短：单事务内禁止循环调用远程、禁止做大 `SELECT ... FOR UPDATE` 批量锁
- 批量任务按 100~1000 条一批提交，批间记录进度

### 8.2 分布式事务

- 优先**最终一致**（TCC / Saga / 本地消息表），性能远好于 XA
- TCC 的 Try 阶段要**冻结资源**（如冻结余额）而不是直接扣减，Cancel 才能安全回滚
- 金融核心的"钱"场景，宁可多写中间状态（`transaction_status=0 处理中`）再异步确认
- 所有跨服务流程必须有**超时 + 主动查单 + 人工兜底**三件套

### 8.3 分布式锁

- 用 DB 行锁或 Redis Redisson（自动续期），锁粒度尽量细（按账户号，不是全局）
- 锁必须有超时；Redis 锁要防误删（value 用唯一 token，释放时校验）
- 金融核心推荐**数据库悲观锁 + 唯一索引兜底**，减少对外部锁服务的依赖

### 8.4 死锁与热点

- 统一表访问顺序（按 ID 升序加锁），避免交叉
- 缩短事务，失败立即回滚重试
- 应用层做**死锁重试**（识别 1213/1205 并重试）
- 热点行用分段（segment）打散写

## 11. DDL 变更管理

### 11.1 禁止在生产直接执行的 DDL

| 场景 | 方案 |
|---|---|
| 加字段 | `gh-ost`（`pt-osc` 在 MySQL 8.0 触发器模式下有坑，优先 gh-ost） |
| 改字段类型 | 同上；大表改类型必须先在等量级压测表验证 |
| 加索引 | `gh-ost`，避开月末/季末 |
| 删字段 | **三步走**：① 代码停止读写 → ② 观察 ≥ 2 个发布周期 → ③ `gh-ost` 删除 |
| 索引清理 | 逐个删，每次删完观察 24h |
| 大表 DDL | 低峰期、限速、监控复制延迟 |

### 11.2 变更流程

1. 提交 DDL 脚本 + 变更说明（影响行数估算、预计耗时、是否停写、**回滚脚本**、**验证 SQL**）
2. DBA + 架构双评审（金融系统建议四眼原则）
3. 影子库/预发用生产量级数据演练，记录耗时
4. 生产低峰执行，实时监控 QPS、复制延迟、慢查询、锁等待
5. 执行后立即验证：行数一致、索引生效、关键查询计划未劣化、**`MAX(id)` 与 `AUTO_INCREMENT` 值一致**
6. **每次 DDL 变更必须有回滚脚本**

全部登记在 `admin_schema_change_tab`：**变更单号、DDL 全文、回滚 SQL、验证 SQL、执行工具、预计/实际耗时、影响行数、执行人、复核人（必须与执行人不同）、验证结果**。

### 11.3 索引变更

- 新增索引前先在压测库验证写入性能下降幅度
- 删除索引前确认无慢查询依赖（查 `performance_schema.table_io_waits_summary_by_index_usage`，`index_io_reads=0` 持续 7 天才可删）
- **禁止一次性删多个大索引**

### 11.4 禁止的"优化"手法

- ❌ `ALTER TABLE ... FORCE` 重建全表
- ❌ 生产环境 `OPTIMIZE TABLE`（本质是重建表）
- ❌ 关闭 `innodb_flush_log_at_trx_commit` 换性能（除非有正式风险审批）
- ❌ 跳过 binlog 以加快写入（断电即丢数据，金融禁）

### 11.5 发布兼容

- 蓝绿/滚动发布，DB 变更与应用发布**解耦**
- **前后兼容期**：Expand → Migrate → Contract 三步法
- 灰度：按客户号尾号/白名单
- **回滚必须在 60 秒内完成**（一次回滚失败 = 烧掉 7 天预算）

## 12. 可观测性与备份

### 12.1 两层监控

**第一层 —— 基础设施指标**：复制延迟、Threads_connected、锁等待、死锁次数、慢查询、磁盘水位、InnoDB history list length、主从切换事件。

**第二层 —— 业务可用性与错误预算**：

| 指标 | 定义 | 用途 |
|---|---|---|
| `db_unavailable_seconds_total` | 累计 DB 不可用时长 | **直接扣减错误预算** |
| `transaction_success_rate` | 交易成功率（含降级后最终成功） | 真实业务可用性 |
| `transaction_pending_count` | 降级队列中的待补单数 | 慢性渗漏的早期信号 |
| `lock_wait_retry_total` | 锁等待重试次数 | 加锁纪律的健康度 |
| `lock_wait_p99_ms` | 锁等待 P99 | 持锁过长的早期信号 |
| `reconciliation_difference_count` | 对账差异笔数 | **准确性指标** |
| `ledger_balance_check` | 借贷平衡校验结果 | 准确性 P0 指标 |

**告警用 burn rate 而不是固定阈值**：
```
示例: 30 分钟窗口内交易失败率 > 5%
  → 消耗 0.05 × 1800s = 90 秒预算 → 占年度预算 2.85% → 要求 2 小时内定位
```

**每次数据库不可用事件必须记录到 `admin_database_availability_tab`**。

### 12.2 业务级自检（日终跑批必须包含）

- 借方合计 = 贷方合计（全局与分科目）
- 各账户 `balance` = 该账户分录累计
- `balance_after` 序列自洽（每笔 = 上一笔 ± amount，序列不得断裂）
- 账户余额 = 流水汇总（**独立算一遍，不复用业务代码路径**）

### 12.3 备份

- 每日全量备份 + binlog 增量，**备份独立于主从链路**
- **备份不验证等于没有备份**：每月一次完整恢复演练并计时
- 保留期满足监管；备份加密、异地存放
- 误删场景依赖 `binlog_row_image=FULL` + PITR，**能力必须事先验证过**

### 12.4 慢查询治理

- `long_query_time=1` 起步，日终跑批窗口可临时调到 0.1
- 慢日志采集（pt-query-digest），按 fingerprint 聚合，Top N 每周跟进
- `performance_schema` 采集 `events_statements_summary_by_digest`
- **单条 SQL 超过 1s 在核心链路视为线上故障**，不因为"跑得通"就放过

## 13. 可用性设计（4 个 9）

### 13.1 错误预算

```
年度不可用预算 = 365 × 86400 × (1 - 0.9999) = 3153.6 秒 = 52.56 分钟
每日预算       = 8.64 秒
每月预算       = 4.38 分钟
```

| 故障场景 | 消耗 | 等价于烧掉 | 一年最多 |
|---|---|---|---|
| 主库优雅重启 20s | 0.33 min | 157.7 天预算 | 2.3 次 |
| 主库崩溃 + 自动切换 30s | 0.5 min | 105.1 天预算 | 3.5 次 |
| **人工介入故障转移 3 min** | 3 min | 17.5 天预算 | 20.8 次 |
| 一次 5 分钟故障 | 5 min | 10.5 天预算 | 34.7 次 |
| 一次 1 小时故障 | 60 min | 0.9 天预算 | — |

**慢性渗漏的账更可怕**：

| 日常渗漏 | 折算 | 耗尽全年预算 |
|---|---|---|
| 每天漏 1 分钟 | 每日预算的 6.9 倍 | **14 天** |
| 每天漏 10 秒 | 每日预算的 1.16 倍 | **86 天** |

> **4 个 9 的真正风险不是"某天崩了半小时"，而是"每天都有几笔交易因为各种原因失败、没人注意、连续三个月"。**
> 所以必须**持续测量并累计真实不可用时长**（记账），错误预算要能被扣减。

### 13.2 RTO / RPO

| 指标 | 目标 | 依据 |
|---|---|---|
| 年度不可用时长 | ≤ 52.56 分钟 | SLO 定义 |
| 单次故障 RTO | **≤ 30 秒** | 30s = 105 天预算 |
| RPO | **0**（同步/半同步） | 准确性第一，丢交易比短暂不可用严重 |
| 计划内变更影响 | **0 秒**（零停机 DDL） | 每日预算仅 8.64 秒 |
| 回滚完成时间 | **≤ 60 秒** | 一次回滚失败 = 烧掉 7 天预算 |

### 13.3 应用层降级 —— 把可用性从 DB 层扩展到业务层

**这是 4 个 9 场景下最容易被忽略、也最有效的一招。**

数据库切换需要 30 秒。如果这 30 秒里用户直接收到"系统繁忙"，那 30 秒就是 30 秒的业务不可用。如果是：

```
DB 不可用 → 交易请求写入本地/消息队列 → 恢复后自动补单 → 用户最终成功
```

**用户视角的不可用时长接近 0**，而幂等机制保证补单绝对安全。

- 写路径 DB 失败时，**不直接返回失败**，判断"是否为可补偿的写操作"（转账、扣款）→ 投递到可靠队列，返回"处理中"
- **绝不接受的降级**：返回"成功"给用户但实际没记账。**宁可让用户等，不可让钱对不上**
- 队列必须有幂等消费 + 死信队列 + 人工介入入口
- 补单成功率必须纳入监控

**配套**：应用侧熔断（DB 失败率超阈值 → 快速失败降级）、连接池能感知拓扑变化、上下游能接受"最终结果晚到"。

### 13.4 演练（不演练的高可用 = 没有高可用）

| 演练项 | 频率 | 验收标准 |
|---|---|---|
| 主库宕机自动切换 | **每季度** | RTO ≤ 30s，RPO = 0，人工零介入 |
| 完整恢复演练（备份 → 恢复 → 校验） | **每月** | 记录实际 RTO，账务数据行数与金额合计一致 |
| 锁等待雪崩演练 | 每季度 | 构造热点，验证超时与熔断生效，DB 不被打挂 |
| DB 不可用降级演练 | 每季度 | 交易进队列，恢复后自动补单，笔数与金额完全一致 |
| 幂等重放演练 | 每季度 | 同一幂等键重放 100 次，只入账一次 |

**演练本身不计入对外 SLO，但必须记录并复盘。**

## 14. 准确性加固

### 14.1 三道防线

| 防线 | 位置 | 作用 |
|---|---|---|
| 第 1 道 | **DB CHECK 约束** | 余额非负、发生额为正、方向值域 —— 物理防线，应用层漏了它还在 |
| 第 2 道 | **应用层断言** | 事务提交前自校验：借贷平衡、余额 = 上笔 + 本笔、金额与分录合计一致 |
| 第 3 道 | **跑批对账** | 独立路径重算，不复用业务代码逻辑 |

**第 3 道的对账程序必须独立实现**（直接对 `account_ledger_entry_tab` 求和），**绝不能调用业务代码的余额计算方法**。用同一份代码算两遍，只能发现两次计算之间的不一致，发现不了"两次都算错了"。

### 14.2 对账频率

| 对账类型 | 频率 | 内容 |
|---|---|---|
| 账户余额 vs 分录累计 | **每 5 分钟** | 增量校验最近 5 分钟有变动的账户 |
| 借贷平衡 | **每 5 分钟** | 全局与分科目：借方合计 = 贷方合计 |
| `balance_after` 序列自洽 | **每 5 分钟** | 每笔 = 上一笔 ± amount，序列不得断裂 |
| 渠道对账 | 每日 T+1 | 与微信/支付宝/银联逐笔核对 |
| 全量重算 | 每日 T+1 + 每月 | 从流水重算全部账户余额，与 `account_tab` 比对 |
| 幂等键重复检查 | 每日 | 同一幂等键不得对应多条分录 |

**5 分钟粒度让错误在 5 分钟内暴露，而不是等到日终。**

### 14.3 人工干预留痕

所有涉及资金的人工操作（调账、补记、冲正、限额调整）必须：
- 写 `admin_audit_log_tab`（字段级前后快照）
- **双人复核**（发起人 ≠ 审批人，**系统层面校验**，不能靠流程约束）
- 调账必须通过"反向分录"实现，**严禁直接 UPDATE `account_tab.balance`**
- 提供"任意账户、指定时间范围的流水独立重算"工具，供随时抽查

### 14.4 幂等与补单

- 幂等键全局唯一索引，**幂等键构造规则要全局唯一且文档化**
- 补单/重放必须走与正常流程**完全相同**的代码路径（同一 Service 方法），不允许写一套"补偿专用"的简化逻辑
- 降级队列消费者必须幂等，失败进死信队列后有人工处理入口

### 14.5 会计日历与切账

`batch_business_date_tab` 管理：业务日期、会计日、记账期间、**切账时点**、是否允许记账、关账状态。

**月结关账后，禁止任何对已关账期间的记账操作** —— 这条规则必须在 DB 层或应用层强校验，**依赖代码自觉在关账跑批期间一定会出乱子**。

## 16. 反模式总表

> **这是唯一一份反模式清单。**

### 16.1 金额与精度

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 金额用 `FLOAT` / `DOUBLE` | 尾数误差，对不平账 | `DECIMAL(20,2)` |
| 金额用有符号正负表示借贷 | 方向与金额混用，逻辑缠绕 | `direction` + 正数 `amount` |
| 舍入点散落在各处 | 同一笔业务不同环节结果不一致 | 全局唯一 `Money` 值对象 |
| 分摊尾差未处理 | 分摊合计 ≠ 总额 | 最后一份取"总额 - 已分配合计" |
| 比例存 `%` 数值 | 口径歧义 | 存小数，格式化在展示层 |

### 16.2 事务与锁

| 反模式 | 后果 |
|---|---|
| 非唯一索引 / 范围条件上 `FOR UPDATE` | 间隙锁，锁范围爆炸 |
| 业务代码自己开事务、自己加锁 | 顺序不一致 → 死锁 |
| 按业务方向排序加锁 | 循环等待 |
| 事务内调用外部接口 | 长事务、锁等待雪崩 |
| 事务内做批量查询或大 `SELECT` | 持锁时长暴增 |
| 循环内逐条提交（批量场景） | 吞吐低、一致性无法保证 |
| DAO 暴露通用 `update` | 加锁纪律被绕过（**最危险**） |
| `FOR UPDATE` 加在流水表上 | 范围锁住无意义，阻塞插入 |
| 重试时不重新加锁 | 复用已失效的锁对象 |
| 乐观锁漏写重试 | **静默丢更新** |
| `innodb_lock_wait_timeout` 留默认 50 | 一次超时 = 烧掉 5.8 天预算 |

### 16.3 时间与时区

| 反模式 | 后果 |
|---|---|
| 用 `TIMESTAMP` | 读值依赖会话时区，静默偏移 |
| 用 `created_at` 推导 `transaction_date` | 跨区业务日期算错 |
| 用 `NOW()` / `CURDATE()` | 返回会话时区 |
| Java 用 `LocalDateTime` 写库 | 无时区信息，8 小时偏差，**不报错** |
| `DEFAULT CURRENT_TIMESTAMP` | 依赖会话时区 |
| `BETWEEN` 做时间范围 | 漏 23:59:59.001~.999 |
| WHERE 里对时间列套函数 | 索引失效 |
| `UNIX_TIMESTAMP` 做跨时区业务判断 | 受会话时区影响 |
| 从上次日期累加月份 | 期末截断，逐期漂移 |
| 业务日用统一 UTC+8 切账 | 中亚客户交易记到次日 |
| 依赖 OS 时区 | 容器重启后重置成 UTC |

### 16.4 主键与引用

| 反模式 | 后果 |
|---|---|
| 业务单号直接做主键 | 主键不可变是铁律，改主键 = 灾难 |
| UUID / UUIDv4 做聚簇主键 | 页分裂、索引膨胀、缓存命中率崩 |
| `auto_increment_increment = 2` | ID 白白跳一半，防不住 split-brain |
| 假设 id 连续 | 回滚空洞、删除不复用、批量插入空洞 |
| 用 `WHERE id + 1 = ?` 推算相邻记录 | id=100 可能根本不存在 |
| 跨环境搬运依赖 id | 冲突；必须以业务唯一键为准 |
| 用 id 判断业务日期新旧 | ID 是插入顺序，`transaction_date` 才是会计日 |
| `id` 出现在对外 API / URL | 可枚举、泄露业务量、契约难改 |
| 用 id 做加密/签名 | ID 可预测，签名可伪造 |
| 逻辑删除表唯一索引含 `id` | 唯一性形同虚设 |

### 16.5 字符集与命名

| 反模式 | 后果 |
|---|---|
| 用 `utf8`（实为 utf8mb3） | emoji / 生僻字存不进；8.0.28+ 已弃用 |
| 用 `utf8mb4_general_ci` | 8.0 已弃用；ß 判错；中文排序乱 |
| 业务主键用 `_ai_ci` | 大小写折叠撞唯一键，错误信息看不出原因 |
| 用 `utf8mb4_bin` | PAD SPACE，`'ACC1' = 'ACC1 '` |
| 依赖 MySQL 排泰文 | 无泰文 collation，必须应用层 ICU |
| 组合文字列用前缀索引 | 切碎组合字符，产生半个字形 |
| `VARCHAR` 存时间 | 索引失效 + 格式不一致 |
| 混用不同 collation | `ERROR 1267` + JOIN 索引失效 |
| 表名/列名用缩写 | 读不懂、跨团队协作成本高、后期改名指数级变贵 |
| 视图不带后缀 | 与表重名（MySQL 共用命名空间） |

### 16.6 设计与运维

| 反模式 | 后果 |
|---|---|
| 流水表可 UPDATE | 账不可追溯，对账无基准 |
| 物理外键 + 级联删 | 误删主表 → 级联删流水，灾难 |
| 迁移靠"先查后插"防重 | 并发下重复入账 |
| 直接 UPDATE 余额调账 | 无分录、无审计、无法追溯 |
| 报表查询打核心库 | 影响交易链路 |
| 分布式锁无超时 | 死锁业务不恢复 |
| 生产大表直接 ALTER | 长时间锁表 |
| 删字段一次性删 | 下游报表/ETL 报错 |
| 备份不做恢复演练 | 故障时才发现备份是坏的 |
| 只做应用层金额校验 | 脚本修数/直连绕过 |
| 依赖代码自觉关账校验 | 关账跑批期间一定出乱子 |
| 4 个 9 靠人工兜 | 人工路径 3 分钟 = 17.5 天预算 |

## 17. CI 静态检查规则

> **规范靠人记三个月就破，CI 卡住才有效。**

| # | 规则 | 检查内容 | 级别 |
|---|---|---|---|
| 1 | `lock-for-update-unique-index` | 所有 `FOR UPDATE` 的 WHERE 必须命中主键或 `uk_` 唯一索引 | 阻断 |
| 2 | `lock-single-update-site` | `account_tab` 的 UPDATE 只允许出现在 `AccountLockService` | 阻断 |
| 3 | `no-lock-on-ledger-table` | 流水表不得出现 `FOR UPDATE` / `UPDATE` / `DELETE` | 阻断 |
| 4 | `no-abbreviation-in-table-name` | 表名/列名禁止缩写词 | 阻断 |
| 5 | `table-suffix-tab` | 表名以 `_tab` 结尾 | 阻断 |
| 6 | `index-prefix-with-core` | 索引名带实体核心词 | 告警 |
| 7 | `no-utf8mb3` | 禁 `CHARSET=utf8` / `utf8mb3` | 阻断 |
| 8 | `no-general-ci` | 禁 `utf8mb4_general_ci` | 阻断 |
| 9 | `collation-explicit` | 业务主键列未显式 `COLLATE utf8mb4_0900_bin` | 阻断 |
| 10 | `no-pad-space-bin` | 禁 `COLLATE utf8mb4_bin`（应用 `utf8mb4_0900_bin`） | 阻断 |
| 11 | `no-timestamp-column` | 禁 `TIMESTAMP` 列 | 阻断 |
| 12 | `no-datetime6` | 禁 `DATETIME(6)` | 告警 |
| 13 | `utc-default-expression` | `created_at` / `updated_at` 未用 `DEFAULT (UTC_TIMESTAMP(3))` | 阻断 |
| 14 | `no-now-function` | SQL 中出现 `NOW()` / `CURDATE()` / `SYSDATE()` | 阻断 |
| 15 | `no-float-money` | 金额列用 `FLOAT` / `DOUBLE` | 阻断 |
| 16 | `no-enum-column` | 使用 `ENUM` | 阻断 |
| 17 | `no-foreign-key` | 物理外键 | 阻断 |
| 18 | `no-varchar-time` | `VARCHAR` 存时间 | 告警 |
| 19 | `no-prefix-index-on-combining` | 泰文/阿文列用 `col(n)` 前缀索引 | 阻断 |
| 20 | `no-localdatetime-write` | Java 用 `LocalDateTime` 写库 | 阻断 |
| 21 | `between-on-time` | 时间范围查询用 `BETWEEN` | 告警 |
| 22 | `function-on-time-column` | WHERE 中对时间列套函数 | 告警 |
| 23 | `money-suffix` | 金额列未以 `_amount` 结尾 | 告警 |
| 24 | `comment-missing` | 表/列/索引缺 COMMENT | 阻断 |
| 25 | `charset-consistency` | 同库出现 > 3 种 utf8mb4 collation | 告警 |

```bash
grep -oP 'CREATE TABLE `\K[^`]+' schema.sql | grep -P "(^|_)${ABBR}(_|$)" && echo "❌ 表名含缩写"
# 列名禁止缩写
grep -oP '^\s+`\K\w+(?=`\s+[A-Z])' schema.sql | grep -P "(^|_)${ABBR}(_|$)" && echo "❌ 列名含缩写"
# 禁 TIMESTAMP
grep -P '`\w+`\s+TIMESTAMP' schema.sql && echo "❌ 使用 TIMESTAMP"
# 时间默认值必须 UTC 表达式
grep -P '`\w+`\s+DATETIME\(\d\)\s+NOT NULL DEFAULT CURRENT_TIMESTAMP' schema.sql && echo "❌ 未用 UTC_TIMESTAMP 表达式"
```

### B.1 字符集与排序规则自检

```sql
-- 16. 字符集与排序规则自检 SQL (★v3 新增★)
--     建议接入 CI / 上线卡点。逐条执行, 任何一条不符合预期即阻断上线
-- ----------------------------------------------------------------------------

-- 16.1 是否还有 utf8mb3 残留 (8.0.28+ 已弃用, 未来移除) —— 期望: 空
SELECT TABLE_NAME, COLUMN_NAME, CHARACTER_SET_NAME
FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = DATABASE() AND CHARACTER_SET_NAME IN ('utf8','utf8mb3');

-- 16.2 collation 分布盘点 —— 期望: 仅 utf8mb4_0900_ai_ci / utf8mb4_0900_bin
--      (可选 utf8mb4_ru_0900_ai_ci) / utf8mb4_0900_as_cs
--      若出现 utf8mb4_general_ci → 8.0 已弃用, 立即处理
--      若出现 utf8mb4_unicode_ci → 迁移遗留, 需评估影响
SELECT COLLATION_NAME, COUNT(*) AS 列数,
       GROUP_CONCAT(DISTINCT TABLE_NAME ORDER BY TABLE_NAME SEPARATOR ', ') AS 涉及表
FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = DATABASE() AND COLLATION_NAME IS NOT NULL
GROUP BY COLLATION_NAME ORDER BY 列数 DESC;

-- 16.3 ★业务主键列 collation 检查 —— 期望: 空
--      这些列必须是 utf8mb4_0900_bin; 若为 _ci 会因大小写/重音折叠撞唯一键
SELECT TABLE_NAME, COLUMN_NAME, COLLATION_NAME
FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = DATABASE() AND COLLATION_NAME LIKE '%\_ci'
  AND COLUMN_NAME IN ('account_no','customer_no','transaction_no','voucher_no','entry_no',
                      'idempotency_key','request_no','message_id','batch_no',
                      'channel_transaction_no','reconcile_batch_no','incident_no','change_no',
                      'region_code','timezone','cutoff_time','subject_code',
```

```sql
-- 22.1 会话/全局时区 —— 期望: time_zone 均为 +00:00 或 SYSTEM 且系统本身是 UTC

WHERE TABLE_SCHEMA = DATABASE() AND DATA_TYPE = 'timestamp';

-- 22.3 存量 VARCHAR 存时间检查 —— 期望: 空 (时间就是时间, 不用字符串)
SELECT TABLE_NAME, COLUMN_NAME FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = DATABASE() AND DATA_TYPE IN ('varchar','char')
  AND COLUMN_NAME REGEXP '(^|_)(time|date|at|ts|dt)$';

-- 22.4 时间列精度检查 —— 期望: 无 DATETIME(6) (微秒精度无业务意义, 徒增3字节)
SELECT TABLE_NAME, COLUMN_NAME, COLUMN_TYPE FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = DATABASE() AND DATA_TYPE IN ('datetime','timestamp') AND DATETIME_PRECISION > 3;

-- 22.5 ★写入值是否为真 UTC —— 期望: diff_sec 在秒级
--      若 created_at 与 UTC 相差 8 小时, 说明写入时用了会话时区或 Java LocalDateTime
SELECT MAX(created_at) AS max_created, UTC_TIMESTAMP(3) AS db_utc,
       TIMESTAMPDIFF(SECOND, MAX(created_at), UTC_TIMESTAMP(3)) AS diff_sec
FROM payment_transaction_tab;

-- 22.6 ★业务归属日与区域本地时间自洽性 —— 期望: 0 行
--      分录的业务日必须等于"按其区域时区计算的本地业务日"
--      注意: 跨区转账的两侧分录业务日可能不同, 属正常, 本校验逐条按各自 region_code 判定
SELECT l.id, l.entry_no, l.region_code, l.transaction_date, r.timezone
FROM account_ledger_entry_tab l
JOIN system_region_tab r ON r.region_code = l.region_code
WHERE l.transaction_date <> (
  SELECT DATE(CONVERT_TZ(l.created_at, '+00:00', r.timezone))
)
LIMIT 50;
-- 说明: 该校验用 created_at 反推业务日, 仅对"实时入账"成立;
--       补录/延迟到账场景应改用 occurred_at 反推
--       真正的权威口径是 batch_business_date_tab 表, 跑批按 (region_code, transaction_date) 比对

-- 22.7 切账边界用例 —— 切账时点前后的归属日必须正确
--       期望: 03:59 归属上一日, 04:00 归属当日
SELECT DATE(CONVERT_TZ('2026-01-10 03:59:00', '+00:00', 'Asia/Bishkek')) AS local_0359,
       DATE(CONVERT_TZ('2026-01-10 17:30:00', '+00:00', 'Asia/Bishkek')) AS local_2330,
       DATE(CONVERT_TZ('2026-01-10 22:00:00', '+00:00', 'Asia/Shanghai')) AS cn_local;

-- 22.8 各区域当前业务日速查(跑批用)
SELECT r.region_code, r.timezone, r.cutoff_time, b.business_date, b.accounting_period, b.is_closed
FROM system_region_tab r
LEFT JOIN batch_business_date_tab b ON b.region_code = r.region_code
  AND b.business_date = (SELECT MAX(business_date) FROM batch_business_date_tab x WHERE x.region_code = r.region_code)
WHERE r.is_active = 1;
```

### C.6 时间与时区速查

```sql
-- 23. 时间与时区规范速查
-- ----------------------------------------------------------------------------
-- [类型分工]
--   DATE          -> 业务归属日 (transaction_date / accounting_date / business_date)   [按区域时区]
--   DATETIME(3)   -> 事件时刻   (created_at / occurred_at)           [统一 UTC]
--   CHAR(6) yyyyMM -> 会计期间 (accounting_period)
--   TIMESTAMP     -> 全面禁用 (2038 截断 + 隐式时区转换)
--   DATETIME(6)   -> 不用 (微秒无业务意义, 徒增3字节)
--   VARCHAR 存时间 -> 禁止 (索引失效 + 格式不一致)
--
-- [写入]
--   建表默认值用 DEFAULT (UTC_TIMESTAMP(3)) / ON UPDATE (UTC_TIMESTAMP(3))
--     -> 不依赖会话 time_zone (MySQL 8.0.13+ 表达式默认值)
--   业务 SQL 用 UTC_TIMESTAMP(3) / UTC_DATE(), 禁 NOW() / CURDATE()
--   SYSDATE() 禁用 (STATEMENT binlog 下主从不一致)
--   UNIX_TIMESTAMP() 受会话时区影响, 跨时区业务判断禁用
--   Java 侧: 必须用 Instant / OffsetDateTime 转 UTC
--             禁止 LocalDateTime 写库 (无时区信息, 会当 UTC 存, 实际是本地时间 -> 8小时偏差)
--
-- [连接层] 四处必须同时对齐, 缺一即产生偏差
--   MySQL  : default-time-zone='+00:00'  (不依赖 OS 时区, 容器重启会重置)
--   JDBC   : connectionTimeZone=UTC&forceConnectionTimeZoneToSession=true  (Connector/J 8.0.23+)
--   JVM    : -Duser.timezone=UTC
--   连接池 : 初始化时 SET time_zone='+00:00'  兜底
--
-- [查询]
--   时间范围统一用半开区间 >= start AND < end, 禁 BETWEEN (漏 23:59:59.001~.999)
--   禁在 WHERE 对时间列套函数 (YEAR/DATE_FORMAT/DATE) -> 索引失效
--   差值计算用 TIMESTAMPDIFF(unit, a, b), 注意返回 b - a
--   禁 UNIX_TIMESTAMP(a) - UNIX_TIMESTAMP(b) (小数毫秒丢失 + 时区敏感)
--   期末加月截断到月末 (DATE_ADD('2026-01-31', INTERVAL 1 MONTH) = 2026-02-28)
--     -> 计息/分期场景必须从原始起算日重算, 不能从上次日期累加
--
-- [业务归属日]
--   按账户/客户的 region_code 的本地日历计算
--   切账时点按区域本地时间 (system_region_tab.cutoff_time, 常见 04:00)
--   本地时间 < 当日切账时点 -> 归属上一日
--   跨区转账两侧记账日可能差 1 天 -> 流水表带 region_code, 对账/报送按区域出数
--   created_at 不可用于推导 transaction_date (时区会算错)
```
