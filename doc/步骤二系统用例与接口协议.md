# 步骤二：协议与委任的系统用例、规则及接口

本轮范围经用户确认：代理协议、物流委任、报关服务合同/授权；补正改版、公共协议有效期复用和预付认可；第三方电子签，浏览器只发起实名签署，不要求供应商设备或自管私钥。仍为设计/离线原型，没有部署服务或真实平台接入。

## 1. 基线与边界

权威实体为主方案`assets/domain-model.js`，旧`doc/领域实体设计方案.html`只是入口。本步骤对应总览N02/N03/N04；步骤一仅供应商和付款方首次/修改资料，其他主体不是步骤一提交者。步骤二合同签署方可在第三方平台实名参与；其身份及用章授权必须独立核实，不因供应商填了联系人就自动有签约权。

供应商—出口代理协议用途10，供应商—物流公司合同11，供应商—报关代理合同12，分别一单一签、trade+用途唯一身份；同一合同改版不能新建身份绕开唯一性。物流真实委托人若不是供应商必须核实补充委托链，未澄清停止，不凭旧模板认定出口代理是甲方。用途13是正式报关电子委托，不是第三方签合同自动产生的事实。

逐交易合同版本必须引用**原因2批准交易快照**，不是直接引用步骤一当前修订。本轮补“汇总送审签约依据”和“独立审核”两个用例闭合前置。批准前必需项按**签约依据阶段**核实主体/角色、付款关系、CNY、收付路径/付款分支、代理范围、适用资质/报价；未来运输具体时间等仅在本阶段非必需时显式待补。合同本身不作为本次批准的循环前提；此批准不是签约/付款全门禁通过，更不能凭状态8就付款。

本轮合成步骤二使用新合成交易`TRD-S2-DEMO-001`；步骤一真实本地演示库仍状态2/修订4，**不会伪称它已有批准快照或对其补写数据**。参考输入/输出与实体映射见`doc/examples/step2/`，均为未执行的设计例。

## 2. 九个完整目标用例

| 用例 | 参与者与目标 | 结果与失败保证 |
|---|---|---|
| 确认并送审签约交易依据 | 供应商补齐资料，出口代理运营人员核对后送审 | 保存这一版完整送审资料，等待独立审核；被退回后先修改再重送，送审人不能自批 |
| 独立审核签约交易依据 | 独立审核员查看送审原文，批准或写明退回原因 | 保存批准版本或退回意见；审核员不能是填报人或送审人 |
| 起草代理、物流或报关合同 | 供应商选择合同用途，填写双方、正文和有效期 | 以已批准交易为依据建立草稿；上传正文不代表已审核或签署 |
| 独立审核合同条款和委托链 | 独立审核员核对正文、主体、费用、报价和委托关系 | 通过后等待签署，退回后重新补正；合同审核不能改写交易批准 |
| 补正或更正合同版本 | 供应商或有权委托方说明修改原因，另备新版 | 未送审草稿可直接改；送审后另建版本。先查清进行中或结果不明的签署任务，旧证据不覆盖 |
| 发起并完成第三方实名签署 | 合同各方在平台实名签署已审核正文 | 系统先保存任务再联系平台，结果不明查原任务；浏览器跳回或收到通知不能单独证明已签署 |
| 核验签署结果并确认生效 | 后台核实证据，出口代理有权人员确认生效条件 | 签署证据齐全并归档后记已签署，生效条件满足后才生效；替代旧版须正式授权，新草稿不终止旧合同 |
| 逐交易引用有效公共协议 | 供应商为本笔交易选择指定的物流框架协议版本 | 核对主体、用途、范围、有效期和服务单；申请作为交易更正等待重审，不回填原批准资料 |
| 登记正式委托与预付认可 | 供应商提供正式报关委托；预付时由出口代理认可同一报关代理 | 保留正式凭据和认可记录，范围、期间和主体须相符；尚不代表允许付款或已向海关申报 |

每用例有黑盒与单体展开两图（18图），规则、HTTP/Proto及输入输出同屏；默认70%。补正后的送审/签约重新走同一用例，不建冗余“补正完成”生命周期。

## 3. 操作证据与第三方电子签

浏览器采用HTTPS、已核实主体/经办授权、强认证、显示完整内容及明确确认；`X-Confirmation-Id`/RPC confirmation-id绑定原意图，不嵌统一私钥。内部入口以独立内部受众申请确认，不能用外部凭据访问内部。第三方电子签平台承担签署人认证、签署意愿/用章授权及受控密钥签名，服务端验证并归档原件/证书及时间/授权证据。HTTPS、短信、勾选、IP、平台回执均不能单独等同可靠合同签名。

参考[电子签名法官方文本](https://wap.miit.gov.cn/zwgk/zcwj/flfg/art/2022/art_4ed0e4a46946479c90a9e0f2c76a11ef.html)第8、13、14条；法律采信依实际身份/授权、私钥控制、完整性和证据保全，不自动作法律保证。国内机构按适用国密及认证资质选型，国外RSA/ECC按平台确认套件；**不得因浏览器不支持SM2就降级成“已满足国密”**。

法大大等仅作为公开产品类别示例，不固定厂商。`signature-notifications`是本应用归一化入口，**不是杜撰某厂商API**；适配器必须先按选定厂商协议验原报文/签名/时效/重放，再归一化。厂商SDK、端点/签名头/证据格式/速率需正式选型联调，未确认不得上线。

### 平台任务和回调恢复

1. 新发起需当前确切待签署版4/已审文件与主体一致，无其他活跃任务。BEGIN按交易根→合同根/版→门禁→文件→确认→任务固定锁序**先查**，持久`clientReference`/合同号版/审核正文摘要/签署人授权引用/原键/阶段，消费确认同COMMIT；主键和合同版唯一活跃绑定兜底。
2. COMMIT后进程内处理器先按原clientReference查单，确定不存在且平台支持同引用幂等才发起；连接3秒/单次10秒，HTTP应用8秒不足则后台继续，不能在根锁期间等待。UNKNOWN保存dispatch_unknown；不换引用。平台无唯一幂等/查单能力转人工核实，不能假设未建。
3. 应用启动/每5秒恢复扫描，租约60秒/20秒续租及栅栏，8次/24小时发起恢复预算；状态pending_dispatch/dispatch_unknown/awaiting_signers/verifying/archived/rejected/manual_action仅中间件状态，不重复合同生命周期。实际用户签署期限独立由双方/平台确定，到期仍须平台确定终态。
4. 个人签署会话由服务端解析当前身份属于哪位必要签署人；POST只允许白名单本地returnRoute，平台跳转域名白名单、state/nonce绑定。先短事务持久本人的会话准备任务，201只返回pending及`/api/v1/signing-sessions/{id}`。平台取链接连接3秒/总10秒走后台，不挤入应用8秒同步预算；GET本人会话ready才返回受控短期URL/有效期。过期GET明确expired、不发新能力；POST同键始终回放原pending受理投影，过期需新键新确认但不重复创建法律签署任务。敏感URL不进原受理投影、平台回执、普通审计或事件，不接受任意外部returnRoute。
5. 回调专用凭证/原报文签名/时效/防重放，不用供应商Cookie、确认号或前端“完成”标记。providerCode来自验证后的登记集成；事件唯一(providerCode,providerEventId)，同键异文409并隔离告警。先受控保全原报文，BEGIN先查原事件，持久归档任务后COMMIT才201/重放200 received；接收不代表签署/生效。回调验签失败401、机构不匹配403，存储不可用503不得假应答。
6. 乱序/重复/迟到不回退已核实终态；通知后原任务查单并核对任务号/clientReference/合同版/所有签署方/审核正文关联。旧版任务的真实签署结果不能丢弃：隔离保留法律证据并告警，禁止推进新版本，转法律处置。轮询至少30秒，平台频率优先且限预算；异步任务定时恢复，不只等通知。
7. 下载签署件/证据包固定对象键，校验实际字节、扫描/证书/吊销/可信时间/全部签署人、签名覆盖及附件。签署通常改变字节，不能要求签署文件hash等于原审核文件；须验证原正文关联和差异。校验/存储任一步未知都不得置5，回调不能绕过此门禁。
8. 短事务先查既有原结果，再核对任务/原版未被撤销处置，元数据、`signed_file_revision_id`确定一次、状态4→5与ContractSigned证据同COMMIT。平台通知已完成、本地归档失败仍verifying自行恢复。5→6另由有权者确认条件，正式替代与旧版6→7同事务，锁多版按版号升序；未知签署/法律义务不能简单作废。

任务使用同应用既有集成/文件恢复机制的基础设施记录（稳定外部请求绑定、通知唯一键、阶段/租约/栅栏/结果），不新增合同核心表或独立服务。业务状态和中间件恢复状态不是两套可写权威结论。

## 4. REST/RPC接口约定

完整机器可读方法表`doc/examples/step2/http-contract.json`逐项对应`proto/trade/contracts/v1/contracts.proto`及页面；共26个方法（含2个内部确认、6个审查补齐的读/恢复/终止方法）。资源方法：

| 场景 | 资源 |
|---|---|
| 签约交易依据送审/决定 | POST `/internal/v1/trades/{trade_number}/review-submissions`、`/review-decisions` |
| 合同身份/确切版本 | POST `/api/v1/contracts`；GET `/api/v1/contracts/{contract_number}`、`/revisions/{revision_number}` |
| 草稿修改/新增版本 | PUT原`.../revisions/{revision_number}`；POST `.../revisions` |
| 合同送审/审核 | POST `.../revisions/{revision_number}/review-submissions`；内部同资源`/review-decisions` |
| 签署请求/查询/会话 | POST `.../revisions/{revision_number}/signature-requests`；GET `/api/v1/signature-requests/{signature_request_id}`；POST其`/signing-sessions` |
| 平台通知 | POST `/api/v1/signature-notifications`（专用外部凭证） |
| 生效决定 | POST `/internal/v1/contracts/{contract_number}/revisions/{revision_number}/activation-decisions` |
| 公共协议适用 | POST `/api/v1/trades/{trade_number}/agreement-applications`；GET其`/{application_id}` |
| 报关授权/认可 | POST `/api/v1/trades/{trade_number}/customs-authorizations`；POST `/internal/v1/trades/{trade_number}/customs-agent-recognitions` |
| 内部确认 | POST `/internal/v1/operation-confirmations`；GET `/internal/v1/operation-confirmations/{confirmation_id}` |
| 供应商签约依据 | GET `/api/v1/trades/{trade_number}/contract-basis`，仅供应商本方批准资料及当前交易标签，不返回付款方声明 |
| 内部审阅/补充恢复 | GET `/internal/v1/trades/{trade_number}/review-context`；POST `/internal/v1/trades/{trade_number}/revisions` |
| 内部合同审阅/终止 | GET `/internal/v1/contracts/{contract_number}/revisions/{revision_number}`；POST其`/termination-decisions` |
| 本人签署会话查询 | GET `/api/v1/signing-sessions/{signing_session_id}` |

API路径英文是协议标识，不是业务角色缩写。所有POST创建的是提交/决定/请求/适用记录等名词资源，不用`:sign`等RPC动作URL。201＋Location指向受理资源，重放200原Location/最小受理结果；草稿PUT仅已存在编辑态、200，不能upsert。GET只读，未知/不可见404。新资源投影如review-submissions/{id}、review-decisions/{id}及activation-decisions/{id}可由所属资源GET扩展查询，当前以原键POST恢复原受理；**Location是该资源稳定标识，不保证本轮已开放每个标识的GET方法**。

用户写均带`Idempotency-Key`；平台通知例外，以(providerCode,providerEventId)去重，不要求用户键/标签/确认。除创建合同身份/创建确认外，修改/送审/审核/签署/生效/公共适用/授权/认可/重开/终止均须`If-Match`。合同ETag绑定合同号、根当前工作版、目标版、生命周期尾事件及同库受理账本单调游标，不能只用revision_number或正文hash（同正文两次PUT也须防ABA）。不暗加contract_record_tab不存在的version列；游标由账本该根最近受理序号在根锁下维护/读取。交易标签绑定trade_record_tab.version/当前内容修订，状态命令也递增version。签署任务GET/创建返回同一task_version强ETag，创建个人会话前读取此标签；通知不使用用户标签。缺标签428，旧412；同键同文回放先于当前标签/状态，但每次当前授权仍检查。确认创建采用步骤一规范，内部独立受众；创建确认不用If-Match/递归确认。

强ETag不从客户端自报状态得出。客户端不能写actor、签署成功、证书核验通过、状态、生效时刻或平台任务号；均来自认证/验证的服务端事实。闭合类型、重复/未知JSON键拒绝。十进制字符串CNY，uint64字符串、UTC毫秒时间；合同DATE沿权威实体采用Asia/Shanghai自然日**首尾均含**`[effectiveFrom,effectiveTo]`，结束日次日00:00起禁止新使用，不与银行DATETIME半开区间混淆。可空结束日仅逐单按履约结清，不适用公共协议。

### 超时、重试与错误

- 所有GET：客户端/RPC deadline5000毫秒，应用4000毫秒。POST/PUT（含通知、内部确认）：10000/8000毫秒；客户端总预算含连接/等待/重试。创建签署任务201只表示本地持久，平台工作走后台，不能扩张同步deadline等待签完。
- 与步骤一相同连接池500毫秒、锁1秒、事务墙钟2秒；处理预算不足不开事务。RPC必须显式deadline，缺400/INVALID_ARGUMENT DEADLINE_REQUIRED，超长裁剪；HTTP已断连可能没有实际响应。平台调用连接3秒/总10秒，长下载30秒一阶段，原对象/任务有界后台恢复，SDK不叠加重试。
- 同键重试最多3次含首次，预算内100/300毫秒抖动，429/临时503按Retry-After；未知COMMIT先主库核实，不换键。平台签署中不能以“超时”推定拒绝/取消。人工恢复沿原任务，保留审计，不重置attempt_count掩盖失败。
- HTTP问题详情使用filing.HttpProblem；非OK RPC `google.rpc.Status.details`包含同包RpcFailure。常用400 INVALID_INPUT/UNKNOWN_FIELD，401 UNAUTHENTICATED/REAUTHENTICATION_REQUIRED/CONFIRMATION_EXPIRED，403 FORBIDDEN/REVIEWER_NOT_INDEPENDENT，404 NOT_FOUND，409 IDEMPOTENCY_CONFLICT/CONTRACT_ALREADY_EXISTS/SIGNATURE_IN_PROGRESS/PROVIDER_EVENT_CONFLICT/CONFIRMATION_MISMATCH/CONTRACT_STATE_CONFLICT，412 REVISION_CONFLICT，428 IF_MATCH_REQUIRED，422 TRADE_BASIS_NOT_APPROVED/CONTRACT_PURPOSE_NOT_REUSABLE/AGREEMENT_NOT_APPLICABLE/SIGNATURE_EVIDENCE_INVALID/AUTHORIZATION_NOT_APPLICABLE/REQUIRED_MATERIAL，429 RATE_LIMITED，503 DEPENDENCY_UNAVAILABLE/COMMIT_OUTCOME_UNKNOWN/RECEIPT_NOT_READY，504 DEADLINE_EXCEEDED、500 INTERNAL_ERROR。对应gRPC分类见下面。

| 分类 | gRPC状态 | 恢复 |
|---|---|---|
| 400及422字段/证据/适用错误 | INVALID_ARGUMENT | 修正/补件，不自动把拒绝变成功 |
| 401 | UNAUTHENTICATED | 重新认证/确认；无设备不等于跳过实名 |
| 403 | PERMISSION_DENIED | 不降低岗位/签署授权 |
| 404 | NOT_FOUND | 不猜号越权 |
| 409同键异文/重复身份/平台事件冲突 | ALREADY_EXISTS | 查原结果，异文停止/隔离 |
| 409状态或进行中，412/428 | FAILED_PRECONDITION | 原任务查询或GET合并，不能换键盲重做 |
| 429 | RESOURCE_EXHAUSTED | Retry-After及原总预算 |
| 503 | UNAVAILABLE | 明确outcomeUnknown；平台发起未知也保持门禁 |
| 504/客户端无响应 | DEADLINE_EXCEEDED | 写入结果未知先查 |
| 500/客户端取消 | INTERNAL/CANCELLED | 告警或停止等待，不证明已回滚 |

未列出的错误不得默认为成功；共用405/415及机构签名错误按步骤一规范。平台专有错误归一化后保留脱敏诊断引用，不泄露身份证号/访问URL/密钥。

## 7. RESPONSE、cURL、ReqMsg与RspMsg

[完整HTTP示例](examples/step2/http-reference.md)逐个列出全部26个方法的**响应状态、响应头、JSON正文和cURL**；[HTTP JSON](examples/step2/http-examples.json)与[RPC JSON](examples/step2/rpc-examples.json)共用输入输出。每例独立标注未执行前提，特别已签/生效受理例不是伪造的真实成功轨迹；外部证据占位不可用于实际调用。

每个方法显式定义`<方法名>ReqMsg`和`<方法名>RspMsg`，例如：

```proto
message CreateContractReqMsg { ContractInput contract = 1; }
message CreateContractRspMsg { Contract resource = 1; }
rpc CreateContract(CreateContractReqMsg) returns (CreateContractRspMsg) {
  option (google.api.http) = {
    post: "/api/v1/contracts" body: "contract" response_body: "resource"
  };
}
```

HTTP正文直接ContractInput→Contract；RPC才有ReqMsg.contract/RspMsg.resource外壳，不能让REST客户端发送RPC包装。GET ReqMsg仍明确路径参数，响应RspMsg是确切强类型资源，不用任意Struct。错误不包进成功RspMsg；google.rpc.Status.details为filing.RpcFailure。Header不靠Proto字段冒充，仍由适配器执行deadline/If-Match/Location/回执规范。

cURL只有占位环境变量，没有Cookie/密钥/生产凭据；使用与示例完全一致的正文、原键、标签申请本受众的新确认后再写，不能把步骤一创建交易的确认借给合同。第三方通知例须按**选定厂商规范对这些确切原报文签名**，不是普通Bearer/用户确认号；未联调不能用示例报文声明真实平台通知。

## 8. 流程—表—接口审查后的执行约束

### 8.1 签约前置与退回可达性

供应商通过原`PUT supplier-filing`填写`exportAgentDetails`收付路径/付款分支、`customsDetails`资质/人民币报价/计价依据/报价文件，物流可填`logisticsDetails`；角色专属字段不能交叉。初次步骤一允许缺后续字段，**签约依据送审必须核实适用必需项**，运营的summary或supportingEvidence不能替代供应商结构化声明。PUT只替换供应商可写组，保留系统管理的官方委托/认可/协议适用记录，不按缺省字段删除这些事实。

内部`review-context`读取当前资料或显式查询`submitted_snapshot_number`的不可变送审内容；快照须属于本交易、对应当前待审提交，响应仍带当前根ETag，不能审核任意历史版。审批规则版本来自服务器本阶段配置，不信客户端任意ruleVersion降低门槛。退回必须reason及非空结构化missingItems，字段或用途至少一项，事件7及待补投影同事务。`POST revisions`在3→2记录15、内容版加1（即使未改内容也加），之后供应商/付款方各改本方再送审，避免UK(trade,revision,reason)重送冲突。8→2记录13并保存新工作基线原因3快照、旧原因2不变；初始影响范围尚待确认时阻断受控动作，实际字段更正后记录差异，不冒称旧法律合同无效。

`TradeReviewContext.evidence`必须同时展开公共适用/官方委托/出口代理认可的强类型只读投影及对应原内容，和所选当前/送审快照保持一致，不能只返回SupplierFiling而漏掉系统管理事实。供应商`TradeContractBasis.currentEvidence`单独展示当前证据及由批准/来源派生的状态，`supplierFiling`仍明确来自approvedSnapshotNumber；不得把当前pending证据混称已批准。两入口均按对象及文件权限过滤，不含付款方私密声明。补充合成例`evidence-review-context.json`仅类型与映射演示，不是已验证的官方文件。

送审一次事务内依次记录14(2→4)、5(4→4)、6(4→5)，三个事件不同事件号；原因1快照source_event指6。批准记录10(5→8)和原因2快照，退回7(5→3)。更正/开始补充是单独用例中的前置操作，不偷偷在终审命令里代填资料。

### 8.2 同一更正批次与既有合同

首次向已批准交易追加公共适用/官方委托/认可时，8→2并新内容版、事件13及原因3；后续同基准原因2、当前状态2且相关主体/分支等依赖未变的追加，沿**同一更正工作链**每笔再递增版/追加事件3，不必每项先重审。5/3或终态禁止直接追加。全部完成最终一次送审/批准；申请资源的accepted表示仅pending_review，GET按来源修订是否纳入后续批准快照派生effective/rejected/superseded，不能永远pending或直接当当前生效门禁。

不得强制所有既有合同都重绑最新批准快照：依据“合同用途/主体及授权/货物与金额/收付及付款分支/条款与期间”按用途冻结审签依赖，重审用服务端差异核对。仅新增协议引用/已核实授权且未改变该合同审签依赖，继续引用旧原因2并记录复核证据；否则阻断新发签/生效/使用，重新审签而保留法律义务。公共适用本身进入新批准快照不会反过来使框架合同重签，避免永久更正循环。依赖检查查不到即阻断，不以相同主体名称推断一致。

### 8.3 合同版本、持久化与受理账本

合同用途/范围/逐单trade在身份创建后不改；所有新修改、送审、审核、新发签、激活及新增版本的previousWorkingRevision都必须匹配current_revision_number。退回3只新增修订；旧2/4在有权正式终止8且平台任务明确无活跃/未知后再开新草稿，不能留着旧待签版继续接受新命令。旧5/6的新草稿不使其失效，激活新5时若存在其他6必须指定该版并具正式法律替代依据、同事务旧6→7；不能省supersedes造成两个6。终止1–6需reasonCode/reason/非空法律依据，可明确处理非当前但仍有法律效力的旧版，未知/活跃签署先处置不终止；7/8终态只允许原键回放，不重开。

内外部确切版本GET均返回有权可见的reviewResult（review_snapshot_json中结论/意见/规则版/审核时刻及受控证据引用），供应商才能读取补正意见；最小受理回执不代替意见查询，不暴露审核员原始证件/认证信息。

`scopeTerms`已删除并保留Proto字段号6：范围条款权威是不可变review_file原文，不增加一个既无表字段又可能矛盾的正文摘要。公共方输入的legalIdentityEvidenceReference只能解析可信、不可变、受保护的身份/授权封套，由服务端展开为主JSON规定的法定名称/国家/识别类型/受保护引用/授权FileRef；不能把输入引用字符串直接存成不符合主JSON的party对象。逐单party_references按contract_party_sequence/party_role_code/participant_sequence_number的snake_case写入，禁止直接复制ProtoJSON camelCase。

新增基础设施`middleware_command_receipt_tab`（**非新增核心业务表**）：`acceptance_id`唯一、`acceptance_sequence`单调唯一、认证主体/组织/受众、原UUID键、规范方法/路径/原标签、request_hmac/key_version/canonicalization_version、root_reference/target_revision、operation_evidence_reference、原accepted_projection/Location/ETag/受理时刻。UK(主体,受众,原键)，按root_reference+acceptance_sequence索引；一个键不能跨方法异文使用。步骤二业务写（除平台通知及确认创建）先查原键，同文原样回放，异文409；无才业务/确认消费/原投影同事务INSERT。并发唯一冲突整笔回滚，新事务先查；不靠JSON数组搜索代替全请求键唯一性。草稿创建/PUT没有伪造ContractSubmitted事件，靠账本留受理历史；有业务事件仍追加主方案事件，不造任意事件名。

修改/新增版本/送审/审查/激活/终止响应为`ContractRevisionReceipt`（合同号/版/当时状态/强标签/acceptanceId），不含可变正文或假的signedFile；GET才读当前完整ContractRevision。POST新版本Location是`.../revisions/{新版本号}`，提交/决定Location是相应集合`/{acceptanceId}`，不能用合同版本号假扮决定ID。平台回执签原冻结投影，不签可变状态或能力URL。合同签发任务/会话的原投影只含稳定ID/首次阶段；当前阶段/链接通过GET读取。

所有事务先非锁定定位原绑定，再按固定序锁：交易根（逐单）或本方机构授权行（公共创建）、合同根按合同号排序、合同版升序、本地授权门禁、文件号版排序、确认、任务及受理账本；拿到根锁后重新查原结果。后台回调/激活也遵守根→任务，不允许另一处先锁任务再回锁合同形成环。长I/O/平台调用/证书核实/回执生成在事务外；回执生成只在确定COMMIT后，自恢复失败不得返回成功形状。
