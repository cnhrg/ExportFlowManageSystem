# 代理出口业务资金流：两清与反洗钱风险分析

> **文档性质：** 基于本仓库现有设计文件与原始凭证的风险识别与控制建议。**不构成法律意见、税务结论或反洗钱定性**；最终定性须由外管局、海关、主管税务机关、收款银行及执业律师按本笔事实分别作出。
>
> **分析口径：** 用户所称「两清」，本报告按代理出口场景下的通行口径理解为：**货物出口环节由通道方（收汇/报关主体）代办、资金与货物流向分离、通道方按固定比例抽取通道费的业务形态**，与「二清」（支付牌照口径的二次清算）区分。两者在本业务中均可能发生，但成因与控制点不同。
>
> **分析基准：** 仓库内 `交付成果/assets/` 全部原型代码、`材料/` 目录原始凭证、`交付成果/资方展示_产品功能原型设计.md`。外部监管依据逐条列于附录。
>
> **收费口径说明：** 本报告对按货值比例收费、货款扣费等内容的描述，是基于原始合同模板及本报告编制时材料的风险识别，不代表当前产品收费规则。当前设计为每笔固定人民币300元服务费由D承担，在首次获批分账时从D已核验可用余额一次性结算；INVOICE申报不触发收费，不按实收本金比例抽佣，且不减少A合同应付。历史凭证与原合同事实保留，正式收费依据及D授权须留存，合同条款须正式修订后方可按新口径执行。

## 一、结论先行

**当前资金流在形式上是合规的代理出口模型，但其内建机制存在一处必须立即修正的「交易性质错配」，以及多处会把业务推向「两清」外观的特征。风险不在设计意图，而在设计与实际凭证的偏离。**

三条核心判断：

1. **最高优先级（须先澄清）**——本笔 CIPS 报文（`材料/步骤5-CIPS系统贷记转账报文…pdf`）业务类型代码为 **GODX（货物贸易）**，但同一笔对应的付款发票 `INVOICE SZ26101401`（`材料/步骤5-付款发票INVOICE…pdf`）标的写的是 **「陆运费 / Land Freight」，属于服务贸易**。**同一笔资金被同时按货物贸易和服务贸易申报**，贸易背景与收汇性质不一致。这不是设计瑕疵，而是实际凭证层面的实质矛盾：若按 GODX 申报而标的实为运费，属申报不实；若按服务贸易申报，则不落入本系统 N13「货物贸易核验入账」的正确路径。系统现有规则**无法发现这类矛盾**——因为 N12 只校验发票与「交易档案」一致，从不校验发票标的性质与银行报文业务代码是否一致。

2. **结构特征上，本业务已具备「两清」的典型外观**——B（龙南市逸泰源跨境电商有限公司）作为**境内发货人 + 收汇人 + 开票人**，而**货物所有权、生产销售单位、出口退税全在 A**；D（吉尔吉斯斯坦 Ilangria Group LLC）付款，**C（俄罗斯买方）收货，付款方与收货方分属不同国别**；原始材料/旧方案记载B按货值比例抽佣、2个工作日内结汇付A及**代垫垫资**。这个组合与业界所称「通道型代出口」高度重叠。**双抬头报关（境内发货人 B + 生产销售单位 A）在文件上是合规的**，但一旦货物流、资金流、发票流、合同流四者不能互相印证，通道业务的外观就成立。当前收费改为D承担固定服务费，详见本报告收费口径说明。

3. **现有系统的合规控制存在明确空白**——`state-model.js` 定义了 12 个状态机，**没有任何一个合规/反洗钱/制裁筛查状态机**；`database-model.js` 的 14 张表中**没有筛查结果、名单命中、受益所有人、风险评级、关联关系图谱等实体**；唯一合规底稿 `R01`（真实贸易/C—D 关系及合规核查记录）在 `business-data.js:208` 状态仍为 **「待提供/确认」**。设计稿 §4.7 承诺的「风险筛查：制裁、AML、出口管制、最终用途」目前**只存在于文档叙述，无数据承载、无状态流转、无阻断能力**。

**风险评级：**

| 风险项 | 等级 | 性质 |
|---|---|---|
| R1 交易性质错配（货物 vs 服务） | **高** | 申报不实 / 贸易背景不实 |
| R2 付款方≠收货方（C≠D，跨国别） | **高** | 两清外观 + 洗钱通道 |
| R3 合规筛查零落地 | **高** | 监管问询无法应答 |
| R4 历史比例抽佣 + 代收代付 + 沉淀资金 | **中高** | 基于原始材料/旧方案的风险识别；当前收费规则已取消比例抽佣 |
| R5 单笔小额化 + 合并汇款的拆分特征 | **中** | 拆分避报（structuring） |
| R6 A/B 权责错位与退税口径 | **中** | 税务/外汇连带 |
| R7 账户与费用抵扣口径异常 | **中** | 资金截留空间 |

## 三、风险项逐条分析

### R1 交易性质错配 —— 最高优先级

**证据（互相矛盾，均为原件）：**

`材料/步骤5-CIPS系统贷记转账报文TFLS00032_SWIFT_CNY_5 000,00(3).pdf`：

```
Business Type Code   GODX          ← 货物贸易
IntrBkSttlmAmt       CNY 5000.00
Order Description    PAYMENT UNDER INVOICE SZ26101401 14/10/2026
```

`材料/步骤5-付款发票INVOICE,SZ26101401(2).pdf`：

```
INVOICE NO.  SZ26101401
事项         陆运费 / Land Freight   Oct (10月) / 2026   CNY 5,000.00
TO           Ilangria Group LLC, Bishkek, Kyrgyz Republic
```

同一笔 ¥5,000，**报文按货物贸易申报，发票标的却是运输服务**。

**风险后果：**

- 若按 GODX（货物贸易）申报而标的实为陆运费 → 属于**申报不实**，触碰出口收汇贸易背景真实性审核；银行在 N13「贸易背景核验」环节本就应比对报关单成交总价与收汇金额，而陆运费不在报关单成交总价内，可收汇额无对应基础。
- 若按服务贸易申报 → 不属于「出口收汇」，而本系统 N13 的「贸易核验入账」「合同累计可收额度」全部建立在前者之上，**整条 N11→N17 路径失去依据**。
- 若业务实质是**为第三国（C 俄罗斯）货物提供陆运服务** → 则这是服务贸易项下的跨境收款，D 是吉尔吉斯付款人、C 是俄罗斯收货人，**服务贸易项下的付款方与受益方不一致**，需服务贸易真实性材料，而非出口单证。

**系统为什么发现不了：** N12 核验规则是「用途、主体、金额、币种及交易档案ID一致」（`node-validation-rules.js` N12-R01），比对对象是**系统内部**的发票与档案；N13 把贸易真实性**完全外包给收款银行**（「银行核验贸易背景、付款关系及合同累计可收额度」）。系统内**没有任何一处把「发票标的性质」与「银行报文业务代码」放在一起比对**，也没有任何一处强制要求收汇性质与 N01 归档的交易性质字段一致。

**控制建议：**

1. N01 交易档案新增结构化字段 `trade_nature`（货物贸易 / 服务贸易 / 其他），并在 N12 核验清单增加硬性规则：**发票标的性质、CIPS/银行报文业务代码、N01 归档交易性质三者必须一致**，任一不一致 → 阻断，不得开票、不得提交贸易核验入账。
2. 增加「运输服务」这类混合标的的专门判断路径：金额不足以构成货物交易价值时，不得默认走货物贸易核验入账。
3. 立即就本笔 `SZ26101401` 与该笔 CIPS 报文向业务方书面澄清资金性质，再决定走哪条核验路径。**这是当前唯一未结的实质风险敞口。**

### R2 付款方 ≠ 收货方（C≠D，跨国别）—— 两清外观的核心

**证据：** D = Ilangria Group LLC（吉尔吉斯斯坦比什凯克，代理行 Eldik Bank），C = 俄罗斯买方。设计稿 §4.1 表格 D 行写「D向B付款确认、付款编号/金额/币种」，并明确「**C与D不一致时，记录商业关系、付款原因和支持资料；无法解释时进入ON HOLD**」。

**问题在于设计把 C≠D 当作「可解释的例外」而非「需要穿透的常态」。** 在本业务形态下，C≠D 恰恰是**结构性的**（B 是通道方，D 付通道费或代 C 付款，C 才是真实买家），不是偶发偏差。系统当前只要求「记录商业关系、付款原因和支持资料」——记录不等于穿透。三处具体缺口：

1. **无受益所有人（UBO）穿透模型。** `database-model.js` 的 `parties_json` 只存「各角色身份、注册号、地址、D—C关系、授权及来源」，没有 UBO 字段、没有股权/控制关系结构。C 与 D 是否关联、D 是否为 C 的关联方或代付方，全靠人工判断。
2. **C/D 关系不进入四流核对。** `entity-flows.js` 资金流的 states/edges 中没有任何一个节点校验 D 与 C 的关联；N22 四流结案只核对主体/合同/实货/报关/资金/退税是否一致，**不核对「谁付钱给谁」与「谁买货」是否讲得通**。
3. **合规章节是空壳。** `R01`（`business-data.js:208`）—— 「待补：真实贸易/主体与 C—D 关系及合规核查记录」，status 仍是 **「待提供/确认」**，suggest 明确要求补「真实交易、受益所有人、最终收货用途、付款关系、适用监管及银行接受依据」。**这是整个 R01 里唯一真正需要外部提供的合规底稿，目前没有。**

**洗钱视角：** 「境外第三方付款 + 货物运往另一国 + 通道方收汇转付」是贸易型洗钱（trade-based ML）的标准形态。真实风险不在于 C≠D 本身，而在于**系统无法证明 C 与 D 之间存在真实商业关系**，于是任何一笔钱都能以「D 是 C 的关联方/代付方」一句话通过，而这句话在事后审计中不可验证。

**控制建议：**

1. N01 强制采集 C 与 D 的**关系类型**（关联/代付/无关第三方/未知）及证明材料（合同、结算安排、董事会或授权文件），并把「未知」设为**硬阻断**而非可记录项。
2. 引入**受益所有人穿透**：C、D、A 的 UBO 均需记录并筛查；当 D 的 UBO 与 C 的 UBO 相同或存在交叉持股时，触发增强尽调而非自动放行。
3. 把「D 与 C 关系」写进 N22 结案条件：关系说不清 → 不得结案。
4. 在四流时间线上把「资金来源地 → 货物目的地」的地理错配做成**可视化异常提示**，让审查者一眼看见吉尔吉斯→俄罗斯的错配。

### R3 合规筛查零落地 —— 文档有、系统无

设计稿 §4.7「合规控制区」承诺了四类能力，逐条核对代码：

| 设计稿承诺 | 代码现状 | 结论 |
|---|---|---|
| 「风险筛查：制裁、AML、出口管制、最终用途等核查证据、规则来源、执行时间、结果和复核人」 | `state-model.js` 12 个状态机（orchestration/node/contract/customs/tax/receipt/payment/fee/account/grant/release/external）**无一合规或筛查机**；grep「合规/制裁/名单/screening」在 state-model.js 中**零命中** | **无状态流转** |
| 「规则引擎：硬阻断 / 人工复核 / 提示三种等级；命中后记录原因、影响节点、责任人与解除证据」 | `rules.js` 的 `evaluatePayment` 只做付款前置校验（14 个布尔位 + 金额/额度），**无规则来源、无命中原因、无解除证据结构** | **无规则引擎** |
| 「主体及授权：实际交易主体、受益所有人、委托链、收货人/付款人关系和有效期」 | `database-model.js` 去重后 14 张核心表（trade_record / trade_snapshot / file_record / organization / user_account / bank_account / fund_allocation / fund_order / fund_flow / role_template / config_record / integration_record / operation_log / audit_task）中**无筛查/名单/UBO/关系图谱表**；`parties_json` 无 UBO 字段 | **无数据承载** |
| 「系统不得自行宣称法定合规」 | 这句话本身是对的 | 表述合规 |

`database-model.js` 全文 grep「合规|制裁|名单|筛查|受益所有人」，4 处命中**全部是 RBAC 语境**（「内部审计合规」角色名），无一是筛查数据模型。按表名去重后共 14 张核心表，其中无一张承载筛查结果。

**风险后果：** 一旦监管（外管局、海关、银行）就本类业务问询「你们做了哪些制裁筛查、命中如何处置、谁复核、依据哪版名单」，系统**无法调出任何证据**。这本身会构成监管处罚理由，且是所有其他风险中最容易被独立触发的一项——它不依赖业务本身是否出问题。

**控制建议（按落地顺序）：**

1. 新建 **`compliance_screening` 表**：`trade_id / screening_type（制裁|出口管制|AML|最终用途）/ subject_role（A–F及UBO）/ rule_source / rule_version / executed_at / result / hit_disposition / reviewer / evidence_path / valid_until`。名单筛查结果**必须按主体+版本+时间留痕**，不可只留布尔结论。
2. 新建 **合规状态机**：`未筛查 → 已筛查无命中 → 命中待复核 → 命中已升级 → 已排除（须留排除理由）`，与 `node` 状态机的 `hold`/`invalidated` 打通——**名单命中应直接置 hold 并阻断 N12 开票与 N17 付款**，而不是只提示。
3. N01 的合规检查从「系统检查并提示」升级为**有记录的门禁**：无筛查记录不得建档终审通过。
4. `R01` 必须在业务上线前补齐，它不是文档工作而是**系统输入**。

### R4 通道抽佣 + 代收代付 + 资金沉淀

**这是「两清」最容易被认定的地方，也是当前设计中最像通道业务的部分。**

代理合同原文（`材料/步骤2-出口货物贸易代理合同(10.16).docx`）：

> 「代理模式：出口代理，乙方**仅提供出口代理资质与通关配套服务**，货物实际所有权、贸易风险、境外客户对接均归甲方负责。」
> 「乙方收到的货款，属于**代收代付**的性质，资金所有权并不属于乙方。」
> 「乙方收到境外外汇货款后 **2 个工作日**内完成对应款项结算并支付给甲方。」
> 「结算汇率约定：按照甲方要求，以乙方收汇当日银行实际汇率进行结算。」

**风险叠加点：**

1. **通道方无货权、无风险敞口，却掌握全部资金流。** B 的角色被合同限定为「资质 + 通关」，这在两清认定中恰恰是最不利的位置——通道方通常被要求承担货权、货损、质量与合规责任。B 全部免责，风险留在 A，但**资金与银行账户在 B**。
2. **代收代付 + 2 日结汇 = 典型资金停留窗口。** 资金到账到付 A 的时间差虽短，但叠加了「合并汇款、多笔分配」（N11）后，B 账户会在短时间内聚合并再释放大量他人资金。这是洗钱识别模型中的典型 **layering**（分层）特征。
3. **沉淀资金风险。** 设计稿明确「本V1场景**不提供退款操作**」，未匹配差额「受限挂账、保留原汇款编号…账龄」。长期看，B 账户会累积**来源不明的滞留资金**。系统对此有意识（「不预设36个月合规宽限、自动退款或到期转收益」），但也意味着**没有任何出口**。
4. **旧方案中的费用直接从货款扣除。** 原始方案曾描述「两项均向D收取，不减少A合同应收」，这在经济实质上可能呈现为通道费收取方式。此为历史风险识别，不是当前收费规则；当前固定300元由D承担，在首次获批分账时从D已核验可用余额结算，不减少A合同应付。

**控制建议：**

1. **引入资金停留时长监控**：入账到释放的时长分布、同一账户多笔并发在途笔数、B 账户沉淀余额随时间增长曲线，进 Boss Viewer 做异常阈值告警。
2. **未匹配差额必须设定强制出口**：账龄超期（如 30/60/90 天）自动升级至人工处置流程（认领 / 退汇 / 移交合规），不可无限挂账。设计稿已明确不设自动退款，那就更需要**人工兜底**与**升级路径**。
3. **落实当前D承担的服务费合同及财税依据。** 正式收费依据须明确D承担固定人民币300元、首次获批分账时从D已核验可用余额结算，并留存D授权；由谁开具何种票据须按实际合同主体和财税规则确认，不应沿用向A单独收费的旧建议，也不得把服务费改为A货款扣项。
4. **明确 B 的责任下限**并写入合同与系统门禁：B 至少对申报不实（品名、数量、货值）与贸易背景不实承担连带责任——这是将 B 从「通道」拉回「代理」的唯一有效方式。

### R5 单笔小额化与拆分特征

**证据：** 本笔实收 CNY 5,000.00（`步骤5-CIPS…pdf`）。

对照《金融机构大额交易和可疑交易报告管理办法》第五条（已核对原文，见附录）：

- **非自然人**客户银行账户间款项划转：**当日单笔或累计 人民币 200 万元以上**（外币等值 20 万美元以上）→ 大额报告；
- **自然人**跨境款项划转：人民币 20 万元以上。

¥5,000 远低于任何一项门槛，**不构成违规**。但须注意三点：

1. 门槛低意味着**单笔小额本身不触发报告**，风险不在单笔，而在**结构**。
2. 设计稿的 N11 机制是「**D 汇总多笔货款合并为一笔 CIPS 汇款**，水单附言逐笔列明交易建档ID及金额」。合并汇款本身是为了匹配多笔交易，但**在监管视角，合并大额反而是降低可识别性、增加拆分痕迹的操作**。系统设计上把附言逐笔列 ID 作为强约束（这是正确的、也是本设计做得最好的一处），但**现实中附言往往不会如实逐笔列明**。
3. 系统缺一个能力：**跨交易、跨日的累计拆分检测**。同一 D、同一收款账户、连续 N 笔接近或低于阈值的金额，目前没有任何聚合视图或阈值告警。`boss-workspace.js` 里与资金相关的只有「待匹配」（5 处）、「阻断」（4 处）计数，**没有金额阈值或频次维度的聚合指标**。

**控制建议：**

1. 在 Boss Viewer 增加**同付款方/同币种/同日的笔数与累计金额聚合视图**，并设置与外管/银行大额门槛对齐的阈值告警线（低于门槛但当日累计异常的情况）。
2. 强化 N11 附言约束：**水单附言未逐笔列明交易建档ID 的来款一律不予关联**，差额进受限挂账。现有规则已有此方向（ID缺失/重复→差异部分挂账），但需在**资金看板可见**，而非只停留在节点内。
3. 合并汇款的 1:N 分配必须保留**原始水单原文索引**，以备银行与外管倒查——`database-model.js` 资金域已有「原附言和原文索引」字段，落地时不要省略。

### R6 A/B 权责错位与退税口径

**证据：** 出口退税由 **A 自行办理**（操作指引 §1、§4.6），而 B 是报关单上的**境内发货人**、是收汇人、是开票人。

这在「代理出口 + 委托方自办退税」模式下是合法路径（委托出口项下由委托方办理退免税）。但风险在于：

- **退税利益在 A，收汇与报关主体在 B。** 若发生申报不实，追责链条会同时指向 A（骗税）与 B（协助/通道），而 B 的合同已全面免责。
- 双重抬头（双抬头报关）使 A 与 B 在报关单上同时出现，**任何一方的单证造假都会同时污染两条线**，责任边界模糊会放大共犯认定风险（参照骗取出口退税罪的从犯认定逻辑）。
- 设计稿 §4.6 已注明「证明申请主体、权限、渠道…以主管税务机关正式确认依据为准」且 `business-data.js:162` 标记 `pending:true`——**这个待确认项至今未闭环**。

**控制建议：** 在 N18/N19 固化「证明申请主体」的前置结论并与退税流强绑定；在合同层面对 B 增加申报不实的连带责任（见 R4-4）；把 A/B 责任矩阵做成系统可查的规则表，而非散落在合同文本。

### R7 账户与费用抵扣口径异常

**证据（`材料/步骤1-B收款信息.jpg` 与 `材料/步骤1-B收款路径-开泰银行开票信息…docx`）：**

B 对外提供 **3 个币种账户**（CNY 1505000000004827 / USD 1501000000004832 / THB 1501000000004832），开户行 **开泰银行（中国）有限公司深圳分行**（KASICNBS）。

异常点：

1. **USD 与 THB 两个币种账号完全相同**（1501000000004832）。同一账号同时标注两个币种，属**账户信息填写错误**，也可能是历史模板复制残留未改。结汇账户信息出错会直接导致收款失败或退汇。
2. **实际 CIPS 受益人账号是 `150500000004827`**（报文原文），与收款信息照片上的 CNY 账号 `1505000000004827` **位数/编号不一致**（前者 15 位、后者 16 位）。以哪个为准必须核对原件——**账户不一致是资金错付与洗钱拦截的核心指标**，系统却在 N11 只校验「交易建档ID、付款主体、币种」，**从不校验实际入账账号与档案账户是否一致**。
3. 收款行在深圳、主体与仓储在江西赣州龙南保税物流中心，**收付主体地与经营地分离**，本身即资金流异常特征。
4. 账户主数据虽然有 `account_fingerprint UK` 与 `owner_verification_json`（`database-model.js` 资金域），但**缺「变更前后账号比对」与「变更原因/授权人」的结构化要求**，设计稿 §4.3 虽提及「账户变更双人核验」，仍属描述层。

**控制建议：**

1. **N11 增加硬规则：实际入账账号必须命中 `bank_account` 档案中的已核验账号（掩码比对 + 账号指纹），不命中即挂账并升级人工**，不允许只凭金额与附言关联。
2. 立即核对上述三个账号（CNY/USD/THB）的真实开户信息，修正收款信息模板，**尤其 USD 与 THB 同号问题**。
3. 账户变更实行**冷静期 + 双人核验 + 首次小额验证**，变更后短时间内大额入账自动告警——这是账户替换类洗钱的通用手法。

## 四、系统设计做对了什么

为免评估失衡，以下机制是本设计**真实有效**、且在同类系统中并不常见的优点，建议在补强时保留：

| 机制 | 位置 | 价值 |
|---|---|---|
| CIPS 清算成功 ≠ 贸易核验入账成功，二者严格分离 | `state-model.js` receipt 机、`process-data.js` N13 | 阻断「付款即合规」的错觉 |
| 三重证据齐备才释放（贸易核验 + 实际入账 + 可用确认） | N13-R02 | 资金释放条件严格 |
| 资金分桶：CNH 不可用 → 国内人民币可用 → 费用预留 / 付款锁额 | `database-model.js` 资金域 `bucket_from/bucket_to` | 结构性地防止「未核验资金被用于付款」 |
| D服务费结算与A合同应付分项核验，不虚增贸易额 | 当前设计稿 §4.4 | 保护A合同应付并留存D承担依据 |
| 未匹配差额受限挂账，不得开票/付款/转收益 | N11-R02、N13-R03 | 阻断挪用未核验资金 |
| 版本失效链：改件 → 旧批准逐级失效 → 重审 | node 机 `invalidated` | 防「改单绕过复核」 |
| 收益划转双边流水核清，单边/未知保持锁定 | N14-R03 | 防「扣费成功」被误认为「B 实际获利」 |
| 内部批准 ≠ 外部审批，职责分离 | 全流程 | 反洗钱内控基本盘 |

**这些机制在「合规代理出口」前提下是有效的。风险不在于它们失效，而在于它们管的是「钱的流转是否可控」，管不了「这批交易本身是否真实」——后者正是 R1/R2/R3 的缺口。**

**关于「两清」与「二清」的区分：** 「二清」为支付牌照口径——无证机构留存商户结算资金并自行清算，核心是支付业务资质与备付金监管；「两清」在本报告语境下指代理出口场景中**货物出口环节由通道方代办、资金与货物流分离、通道方按比例抽佣**的形态。两者成因不同，但**在本业务中叠加出现时会相互放大**：B 若同时提供无牌二次清算与通道型代出口，其在监管眼中的画像将从「代理服务商」转向「资金通道」，所有笔业务均会被穿透审查。
